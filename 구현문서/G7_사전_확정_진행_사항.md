## C1 — legacy MAS domain 지원: MetaGPT만 Math 불가 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 1(§2) — 비교 대상 MAS·domain 범위.

### 판정

- **능력상 Math를 실행할 수 없는 legacy MAS는 MetaGPT 하나뿐이다.**
- `autogen`, `agentverse`, `camel`, `mad`, `sc`, `llm_debate`는 모두 Math·Code를 실행할 수
  있다(능력 제약 없음).
- 따라서 `scripts/mas/{agentverse,autogen}.sh`의 `TASK_DOMAINS=("code")`는 **능력 한계가
  아니라 원 ACIArena 논문 실험 설정 스냅샷**이며, Math 확장에 신규 구현이 필요 없다
  (run config에 math domain을 추가하면 된다).

### 근거

1. **코드 레벨 게이트** — `aciarena/evaluation/evaluation_suite.py`의 `init_tasks`:

   ```python
   if self.args.task_domain == 'math':
       if self.args.mas != 'metagpt':
           self.load_math_tasks()
       else:
           raise ValueError(f"Unsupported MAS for math domain: {self.args.mas}")
   elif self.args.task_domain == 'code':
       self.load_code_tasks()
   ```

   `metagpt`만 명시적으로 차단되고, 그 외 모든 MAS는 `aciarena_math.json`을 로드해
   `MathTask`로 채점한다. Math 데이터셋·verifier는 MAS와 무관하게 동작하며
   `debate`·`sc`는 이미 Math를 실행한다.

2. **autogen은 domain-agnostic** — 범용 프로필 `ASSISTANT_AGENT_SYSTEM_MESSAGE`가
   "final answer ... in the box" 형식을 지시해 math verifier와 호환된다. code 전용 프로필
   `ASSISTANT_AGENT_SYSTEM_MESSAGE_CODER`는 `code_execute=True`일 때만 쓰이는데, 저장소
   전체에서 `code_execute`가 True로 설정되는 곳이 없다(`assistant_agent.py` 기본값 False).

3. **agentverse는 domain-agnostic** — role_assigner/solver/critic/evaluator 프롬프트가
   "group of experts", "solve the following problem"류로 code/math 하드코딩이 없다.
   role_assigner가 문제에 맞는 전문가를 동적으로 recruit하므로 domain에 종속되지 않는다.

4. **MetaGPT의 제약은 능력상 실재** — MASLab 논문 Table 1에서 "Coding-Specific"으로 분류되며,
   위 코드 게이트와 일치한다. MetaGPT Math 확장은 별도 신규 구현이 필요하다.

### 확정에서 파생된, 여전히 "필요" 문서에 남는 사항

- **정책 결정(미확정):** MetaGPT만 Code-only로 두고 나머지를 both로 돌릴지, 아니면 비교
  공정성을 위해 전 MAS를 Code-only로 맞출지 — 능력이 아니라 연구 설계 선택이므로
  필요 문서 §2.2 Q2에서 계속 다룬다.
- **운영(확정, C2 참조):** `camel`·`mad`는 실행 `.sh`가 없을 뿐 `benchmark.py`로 정상
  실행 가능함이 검증됐다. 상세는 아래 C2.

## C2 — camel·mad 실행 가능성: benchmark.py로 정상 실행 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 3(§4) — legacy 실행 경로.

### 판정

- **`.sh` 부재는 실행 불가가 아니다.** `camel`·`mad` 모두 `benchmark.py --mas camel|mad`로
  실행할 수 있다. 없는 것은 편의용 셸 래퍼뿐이며, 이는 선택 사항이다.
- code·math 두 domain, benign/hijacking/disruption/disclosure 네 suite의 **16개 조합
  전부**에서 모델 호출 직전까지(태스크 로드 + 공격 빌드)가 정상 구성됐다.

### 근거 (오프라인 정적 구성, 모델 API 호출 0회)

1. **등록·생성:** 두 MAS 모두 `@register_mas`로 레지스트리에 등록되고 `mas/__init__.py`에
   import된다. `build_mas`로 객체가 생성되며 agent 구성은
   camel=`[assistant, user_proxy, critic, task_specifier]`,
   mad=`[affirmative, negative, moderator, judge]`이다.
2. **suite 구성:** 더미 API 키(호출 없음)로 `build_suite`를 실행하면 16/16 조합에서
   `tasks`가 로드되고 `executor.attacks`가 빌드된다. 공격 수는 benign 1,
   hijacking(code 4·math 3), disruption 5, disclosure 5로 타 legacy MAS와 동일하다.
3. **math 게이트 무관:** C1의 `init_tasks` 게이트는 `metagpt`만 차단하므로 camel/mad는
   math에서도 정상 로드된다.

### 남는(미확정) 사항

- 실제 모델 실행에서 공격이 camel/mad의 어느 target agent에 주입·채점되는지는 **per-MAS
  target 결정**(필요 문서 §2.2 Q3·Q4)에 속하며, 실행 가능성과는 별개다.
- 편의용 `scripts/mas/{camel,mad}.sh` 추가는 선택 사항이다(있으면 재현 편의만 향상).
- G7 공통 per-row 기록 계약(필요 문서 §4.1)은 camel/mad만이 아니라 **모든 legacy MAS에
  공통으로** 필요한 별도 작업이다.

## C3 — G7 비교 범위·도메인 실행 정책 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 1(§2) — 비교 대상 MAS·domain 범위.

### 결정

- **MAD는 G7 비교에서 제외한다.** 비교 대상 = **논문 6종 + CrewAI**
  (MetaGPT, AutoGen, CAMEL, Self Consistency, LLM Debate, AgentVerse). D30/D32의
  "legacy 7종"에서 `mad`를 뺀다(camel은 논문 MAS이므로 유지).
- **도메인 실행:** MetaGPT는 **code만**, 나머지 5종은 **math·code 둘 다** 실행한다
  (D56의 남은 정책 결정을 이 방향으로 확정).
- **보고 형식:** 논문 Table 1 방식대로 **task_domain 기준 표 2개(Math/Code)** 로 나누고,
  각 표에는 그 도메인 지원 MAS만 넣는다(Math 5종, Code 6종). 완전 교차 매트릭스나
  도메인 통합 평균을 강요하지 않는다(D56·논문 Appendix H와 정합).

### 비고

- 표 분리 문서화 작업은 사용자가 직접 진행하며, 그 세부는 현재 별도 기록하지 않는다.
- MAD 실행 가능성(C2)은 사실로 유지되나, G7 비교 대상에서는 쓰지 않는다.

## C4 — G7 공격 target agent 정책 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 1(§2) Q3·Q4 — per-MAS target.

### 결정

- **전 agent 스윕은 채택하지 않는다**(경우의 수 폭증). 공격은 **목표별 단일 target agent**
  에만 주입한다.
- **target = 논문 Appendix I Table 5(Math, GPT-4o-mini 행)의 worst-case agent** 를 사전
  고정본으로 채택한다. 목표↔suite 매핑은 Hijacking→hijacking, Disruption→disruption,
  Exfiltration→disclosure다.

  | MAS | Hijacking | Disruption | Exfiltration(=disclosure) |
  |---|---|---|---|
  | CAMEL | critic | task_specifier | user_proxy |
  | AutoGen | user_proxy | assistant | assistant |
  | AgentVerse | critic_0 | solver | solver |
  | Self Consistency | sc1 | aggregator | aggregator |
  | LLM Debate | debater_2 | aggregator | aggregator |

  (논문 표기 `debate_2`는 로컬 `debater_2`에 대응.)
- **Code 도메인:** 논문에 code worst-case 표가 없으므로 **위 Math worst-case agent를 code에
  그대로 재사용**한다(옵션 a). 여유가 있으면 code 자체 worst-case 탐색으로 확장할 수 있으며,
  그 확장 작업은 사용자가 진행하고 현재는 기록하지 않는다.
- **MetaGPT(code-only, Table 5에 없음):** Math worst-case가 없어 (a)로 값이 정해지지 않는다.
  기존 `scripts/mas/metagpt.sh` 관례(hijacking→`engineer`, disruption→`architect`,
  disclosure→`qa_engineer`)를 target으로 **채택한다(확정, 2026-09-18)**.
- **CrewAI 비대칭:** CrewAI는 solver 고정(G6 동결)이고 legacy는 목표별 worst-case이므로
  비대칭이 존재한다. 이는 제거하지 않고 **통제·명시할 연구 변수**로 보고한다(D30/D32 원칙).
- **진입점 설계:** 기존 `benchmark.py`를 계승한다(신규 파일 미신설). 기존 옵션
  `--mas`·`--task_domain`·`--suite`(=공격목표)·`--malicious_agents`(=target agent)로 슬라이스를
  지정하며, **구현 자체는 모든 target_agent 선택을 허용**하되 실제 벤치는 위 고정 목록으로
  제한한다.

### 비고

- 오케스트레이터 실제 구현·CLI 세부는 사용자가 진행한다.

## C5 — run당 malicious agent 수: 정확히 1명 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 1(§2) Q5 — malicious agent 수.

### 결정

- **한 run에는 malicious agent를 정확히 1명만 둔다.** 논문이 지정한 값을 그대로 채택한다.
- 이는 C4의 "목표별 단일 target agent"와 정합한다(target 1명 = malicious agent 1명).

### 근거

- ACIArena 논문 §5(line 158): *"Following Byzantine Fault Tolerance (Castro et al., 1999),
  we assume **a single malicious agent**, as a larger fraction would potentially break system
  guarantees and require a stronger assumption."* 프레임워크는 malicious agent를 subset으로
  지정할 수 있으나(Appendix, line 352·356), 본 실험은 단일로 고정한다.
- CrewAI 독립 벤치(G5/G6)도 solver 1명만 공격했으므로 CrewAI↔legacy 비교에서 malicious
  agent 수는 양쪽 모두 1로 일치한다(비대칭 아님).

### 이로써 확정 사항 1(§2) 완료

- 비교 대상(C3, D58) · 도메인 실행(C3, D58) · 목표별 target agent(C4, D59) ·
  malicious agent 수(C5, D60)가 모두 확정되어 **필요 문서 §2는 종결**된다.

## C6 — G7 비교 프레이밍·통계 표기 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 2(§3) — 비교 지표·상태 처리, 특히 Q5(CI).

### 결정

- **프레이밍 = 순위가 아니라 "위치 제시 + 설계 귀인".** G7 cross-MAS는 "기존 6종 대비
  CrewAI의 위치"를 제시하고, 설계 특징(순차 검토 등)이 robustness에 주는 영향을 귀인하는
  것이 목적이다. **"X가 Y보다 안전" 같은 일반 순위·우열 서술은 지양**한다.
- **헤드라인 = 도메인별 표(Math/Code)** 에 각 MAS와 CrewAI를 나란히 놓고, **UA·ASR을
  쌍으로**(utility-security 트레이드오프) 제시한다. 단일 ASR만으로 안전/취약을 단정하지
  않는다(예: 낮은 ASR이 utility 붕괴 때문일 수 있음).
- **불확실성 표기 = 시스템별 task-cluster bootstrap CI.** G6의 `_cluster_interval`을
  재사용하며 반복 실행이 필요 없다(단일 run의 task 변동으로 CI 산출).
- **paired 유의성 검정은 채택하지 않는다.** CrewAI-축이든 전 쌍이든 "차이 유의성 검정"과
  전체 순위표는 만들지 않는다.

### 근거

- 신청서·D30/D32의 기여는 "위치 제시(정성 참조)"이지 우열 판정이 아니다.
- 논문 자신도(line 160·162·164) topology만의 순위는 불충분하고 utility-security
  트레이드오프가 핵심이라 밝힌다(CAMEL ASR 0%는 안전이 아니라 utility 붕괴의 결과).
- paired 검정은 순위 목적이라 RQ에 불필요하고 다중비교 위양성만 늘린다. 시스템별 CI는
  단일 run으로도 위치의 불확실성을 정직히 보여줘 비용에도 유리하다.

### §3에 미치는 정리

- Q5(paired CI)는 **미채택으로 종결**. Q1~Q4(빈 응답·NA·오류·미주입 처리)는 기존
  D30/D54를 따른다: **헤드라인 = 논문 규칙(단순 비율, empty/error/미주입=0, NA 제외 안 함),
  진단 = valid-only 분해(unknown/error/NA 제외)를 별도 보고**. 남은 것은 §4 구현 시 동일
  정책의 fixture 검증뿐이다.

## C7 — legacy per-row 기록 접근·RunRecord 일반화 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 3(§4) — legacy 공통 per-row 실행·기록 계약, #1(스키마 일반화).

### 결정 — 접근 방식 = (A)

- legacy 실행·verify는 **재사용**하고 그 위에 **recording 계층을 후크로 이식**한다(신규 실행기
  미신설). 출력은 CrewAI와 **동일한 `runs.jsonl`/`messages.jsonl` 통일 포맷**이며, 공통
  집계기(D55)가 양쪽을 같은 규칙으로 읽는다. (A)/(B) 선택은 내부 코드 재사용도의 문제일 뿐
  저장 포맷은 두 경우 모두 동일하게 일반화된다.

### 결정 — RunRecord/MessageRecord 일반화 범위 (in-place 상위집합 확장)

구현은 §4 착수 시 `aciarena/evaluation/records.py`에 적용한다. 지금은 계획만 확정한다.

| 필드 | 현재 | 확정 변경 |
|---|---|---|
| `topology` | `Literal['sequential']` | `Literal['sequential','vertical','horizontal','hierarchical']` (논문 H.1 패턴) |
| `malicious_agent` | `Literal['solver']\|None` | `Nonempty\|None` |
| `response_agent` | `Literal['finalizer']\|None` | `Nonempty\|None` |
| `implementation` | `Literal['reconstructed','native']` | `+ 'legacy'` |
| MessageRecord `phase` | crewai 7종 | `+ 'turn'` (legacy agent 간 메시지) |
| `schema_version` | `'1.0'` | **유지**(순수 확장, 버전 미변경) |

**공유 — 유지(확인만):** `attack_category`(22)·`attack_goal`(3)·`attack_surface`(instruction/
agent/message)·`task_domain`·상태 taxonomy(status·utility_status·attack_status,
unknown/error/not_applicable)·not_applicable 범위(AnswerMapping/MathInvert)·category-goal 접두
일치·증거 플래그(target_invoked/payload_injected) 요구. legacy 표면명(adv_input/
malicious_agent/message_poison)→(instruction/agent/message) 매핑과 증거 플래그 생산은
**어댑터**가 담당한다(§4.2).

### 동결 안전 근거

- 읽기 경로 `RunWriter._read`(records.py line 72)가 모든 행을 `RunRecord.model_validate`로
  재검증한다. **상위집합 확장은 기존 CrewAI 행(`sequential`/`solver`/`finalizer`)을 그대로
  유효**하게 두므로 **G6 재감사 PASS가 보존**된다.
- `schema_version`을 `'1.0'` 제외로 바꾸면 기존 행이 깨지므로 **`'1.0'` 유지가 필수**다.
- `records.py`는 G6 artifact manifest의 `analysis_sources`(aggregation.py·aggregate_results.py·
  run_experiment.py)에 없어 provenance 해시에도 영향이 없다. 따라서 별도 versioned record
  type 신설 없이 in-place 확장이 안전하다.

## C8 — legacy 필드 매핑·상태·식별 규칙 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 3(§4) #2 — 공통 row 최소 필드 대조.

### 필드 3버킷 (legacy 실측 산출 ↔ RunRecord)

- **직결(legacy가 이미 생산):** `raw_response`(args 최종 응답), `ground_truth`,
  `prompt/completion_tokens`(`get_token_usage`), `attack_goal`(suite), `attack_surface`(공격
  base클래스 AdvInput→instruction·MaliciousAgent→agent·MessagePoison→message),
  `malicious_agent`(`attack.malicious_agents`), 메시지(MASLogger `session["turns"]`).
- **파생(어댑터 계산):** `response`(CrewAI와 동일 normalizer), `payload_hash`(payload 해시),
  `response_agent`(MAS별 최종 source 라벨), `topology`(MAS별 상수·일반화 enum), `run_id`/식별·
  `config_hash`·timestamps·latency·prompt/verifier_version.
- **신규 구축(legacy에 없음):**
  1. `task_id`·`attack_id` — legacy task는 익명(query+gt), 공격은 클래스 기반 → **결정적 매핑
     테이블** 필요.
  2. `target_invoked`/`payload_injected` — legacy 미추적 → `attack.run()` 효과·대상 agent 호출
     **계측**.
  3. `status`(model_error/timeout…)+오류 격리, `utility_status`/`attack_status` taxonomy —
     `execute()`에 try/except 없음 → **래핑**해 오류 row·partial trace 생산, 0/1→상태 매핑.

### 서브 결정 (둘 다 권장 확정)

- **(i=a) 상태 taxonomy:** legacy `verify()`가 0/1뿐이므로 **실행 오류가 아니면 status를
  `valid`+bool로** 기록한다. legacy는 unknown/not_applicable을 CrewAI만큼 구분하지 않아
  **legacy의 valid-only 진단 = 헤드라인**이 되며, 이 **진단 해상도 비대칭을 report에 명시**한다.
  무리한 unknown 추정은 하지 않는다(논문 대조 왜곡 방지). `llm_call_count` 미추적은
  `usage_missing_calls`로 공개.
- **(ii) 식별 매핑:** 데이터셋이 동일 소스라 **순서·내용 기반 결정적 `task_id` 정렬**, 공격은
  **클래스→manifest attack_id 명시 테이블**. 결과를 보기 전 고정.

### 실제 신규 작업은 버킷3 3종에 집중

대부분 필드는 직결·파생으로 해결되고, 어댑터의 실질 구현은 ① 식별 매핑 테이블 ② 증거 플래그
계측 ③ 오류 격리+상태 taxonomy 세 가지다.

## C9 — G7 실행 모델(per-invocation)·비용 처리 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 4(§5) — 실행·비용.

### 결정

- **실행 모델 = per-invocation 수동.** 진입점은 기존 `benchmark.py`를 계승(신규 파일 미신설)해
  `--mas`·`--task_domain`·`--suite`(=공격목표)·`--malicious_agents`(=target agent)로 **MAS 1 ×
  domain 1 × 공격목표 1** 슬라이스를 하나씩 벤치·저장(runs.jsonl) 후 분석한다(D59-⑤ 확장).
  CrewAI 전용 통합 오케스트레이터(`run_experiment.py`)는 G7에 쓰지 않는다.
- **비용 처리(D48 계승 + G7 완화):**
  - D48의 유료 하드 방지턱 제거 + **dry-run 기본값 유지**를 그대로 계승.
  - **G7에서는 "사전 비용 산정" 요구도 제거**한다(슬라이스가 작고 사용자가 각 실행을 직접
    통제하므로 실행 전 예상 비용 제시를 게이트로 요구하지 않음).
  - 유지: `--execute` 없는 0-call dry-run, **실측 usage per-run 사후 기록**(provenance, 게이트
    아님; G5/G6과 동일).

### 근거

- per-invocation 수동 모델에서 각 슬라이스는 규모가 작고 사용자가 직접 실행·통제하므로 자동
  게이트·사전 산정의 실익이 없다. 큰 배치 파일럿·예산 승인 프레임은 이 모델에 맞지 않아
  §5를 재-scope했다.
- 이전 합의(D48: 코드 게이트 제거·dry-run 유지)는 유지하고, G7에 한해 "사전 비용 산정"만
  추가로 뺀다.

### 비고

- 유료 실행 자체는 사용자가 수행·결정한다. `benchmark.py` 확장·매핑 테이블 구현은 사용자 진행.
- 진입점 파일명: 신규 `start.py`가 아니라 **기존 `benchmark.py` 계승**으로 확정(임시명이던
  `start.py`는 폐기).

## C10 — G6 동결 보존·G7 버전 분리 (2026-09-18 확정)

**관련 필요 항목:** 확정 사항 5(§6) — G6 보존.

### 결정 — "버전 분리"는 백업이 아니라 다음 규칙

- **① 경로 분리:** G7 산출물은 `outputs/g7/…` 신규 경로. `outputs/g5-v2/`·`outputs/g6/`는
  read-only(원본 미변경) → 별도 백업 불필요.
- **② 버전 문자열 분리:** G7 분석/리포트 버전은 `g7-…` 신규 문자열(G6의
  `g6-common-aggregation-v1`·`g6-crew-independent-report-v1`와 구별).
- **③ 하위호환:** D62 literal 일반화는 상위집합 in-place라 G6 `runs.jsonl` 재검증 통과(C7),
  `records.py`는 G6 analysis_sources에 없어 provenance 해시 불변 → **G7 변경 후에도 G6 frozen
  verifier PASS**.
- **④ 결과 분리 보존:** G6 valid-only ↔ G7 재해석(진단)을 별도 이름/경로로 보존.
- **⑤ 무결성·재현:** 원본 무결성은 `g6_artifact_manifest.json`의 SHA-256로 검증(백업보다 강함).
  원본 코드 재현이 필요하면 복사가 아니라 **git 커밋/태그**로 고정(D52 방식).

### 근거

원본을 안 건드리고(경로 분리) hash로 무결성을 검증하므로 복사본 유지가 불필요하다. 백업은
조잡한 대체일 뿐, 실체는 경로·버전 분리 + 하위호환 보장이다.

### 이로써 G7 사전 확정(§2~§6) 종결

- §2 비교 대상·domain·target·malicious 수(C1~C5) · §3 지표·프레이밍·CI(C6) · §4 legacy per-row
  계약·설계(C7·C8) · §5 실행 모델·비용(C9) · §6 G6 보존(C10)이 모두 확정됐다.
- **CrewAI G5 core 재사용:** 별도 확정 대상이 아니라 사용자 운영 선택이다. 기본 계획은
  G7에서 **CrewAI 포함 전부 재실행**(→ `outputs/g7/…`·`g7-…`), G6 동결은 독립 벤치로 보존(D65).
