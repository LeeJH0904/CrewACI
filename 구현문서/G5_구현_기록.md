## 3. 실행기 구조와 안전장치

`scripts/g5/run_g5_matrix.py`가 매트릭스를 실행한다. domain·goal·phase·repetition별 **20개 group**을
만들어 중복 없는 정확한 **1,056-run union**임을 검사한다(그룹 간 논리 행이 겹치면 예외).

### 3.1 기본은 dry-run

기본 동작은 **외부 호출이 전혀 없는 dry-run**이다. `--execute`는 다음 조건을 모두
충족해야 한다.

1. v2 provider preflight artifact가 계약의 model·temperature·seed와 네 검사 항목을
   정확히 만족해 PASS한다.
2. 같은 v2 config에서 `seed_policy.status = accepted_best_effort`,
   `final_benchmark_ready = true`가 서로 일치한다.
3. 기존 attempt의 token usage가 모두 완전하며, 다음 run 시작 전 누적 정가 비용이 $2 미만이다.
4. 유료 실행의 `--batch-size`는 **1**이다. `--stage all`이면
   `--allow-full-matrix`가 추가로 필요하다.

### 3.2 단계(stage) 분할

유료 실행은 서로 겹치지 않는 본 단계로 나눈다. `smoke`는 본 단계의 사전 고정 8개 행을 먼저
실행하는 **중복 view**이며, 이후 단계에서 자동 resume한다.

| 단계 | logical runs | G4 평균 단순 투영 |
|---|---:|---:|
| smoke | 8 | $0.00565036 |
| benign | 69 | $0.048734355 |
| math-core | 507 | $0.358091565 |
| code-core | 420 | $0.2966439 |
| confirmation | 60 | $0.0423777 |

### 3.3 1-run 배치와 비용 정지선

- v2 기본 `--batch-size 1`이며 **유료 실행에서 1 이외의 값은 거부**한다.
  `--max-batches N`은 해당 호출에서 새로 실행할 배치를 최대 N개로 제한한다.
- invocation별 기본 **신규 비용 정지선 $1.00** (`--session-cost-limit-usd`).
- 비용은 API 응답 후에야 알 수 있으므로 정지선은 **각 run 경계에서** 적용되며,
  마지막 한 run 비용만큼 초과할 수 있다. 전체 $2 상한도 실행 전·후에 검사하지만
  호출 자체의 비용을 선지불 예측해 강제 차단하지는 못한다.
- 이미 완료된 동일 config-hash logical run은 다음 호출에서 자동 제외한다(`--resume`은
  CLI에 남아 있지만 내부 실행은 항상 resume). 실패 attempt 재시도는 명시적인
  `--retry-errors`로만 허용하며 최대 3 attempt다.
- SDK 내부 재시도는 0이다. provider usage가 하나라도 누락되면 비용은 lower bound로만
  표기하고 추가 유료 실행을 중단한다.
- `--stage all --execute`는 `--allow-full-matrix` 없이는 거부한다(전량 유료 실행 추가 opt-in).

### 3.4 기록

실행 중에는 append-only `RunRecord`/`MessageRecord`를 사용한다. 유료 기본 설정에선
각 1-run 배치 뒤 audit·완료·오류·토큰·비용을
`outputs/g5-v2/crewai-g5-final-v2/g5_progress.json`에 원자적으로 갱신한다.

### 3.5 통합 중 발견한 audit 결함(수정 완료)

G5 통합 테스트 중 config audit가 **G0 task manifest 경로를 하드코딩**해, 버전이 다른 G5
snapshot을 drift로 오판하는 결함을 발견했다. audit가 attack manifest와 **같은 디렉터리의
task manifest**를 검사하도록 수정했다. 이후 고유 22개 class의 Math/Code 27개 지원 조합
모두에서 생성·주입·target 도달·평가 기록을 mock으로 확인했다.

## 4. provider preflight

`scripts/g5/preflight_g5_provider.py`는 유료 매트릭스 전에 provider를 점검하며,
기본 출력은 `outputs/g5-v2/provider_preflight.json`이다. **preflight PASS까지는 유료
API 요청 3회**가 필요하므로 credential·과금 상태를 확인한 뒤 실행한다.

- 같은 seed 요청 **2회** + strict JSON Schema Judge 요청 **1회**로,
  snapshot 접근 / seed parameter 수용 / 반복 출력 일치 / Judge 형식을 확인한다.
- 응답 model·fingerprint·content hash·usage는 남기되 **API credential은 기록하지 않는다.**
- 오류 시 provider 예외 원문도 공개 artifact에 쓰지 않는다.

**v2 상태:** 2026-09-13 현재 preflight artifact가 없어 유료 매트릭스는 잠겨 있다.
PASS 보고서를 확인한 뒤에만 §8에 따라 v2 readiness 두 값을 함께 바꾼다.

**v1 실행 이력:** 초기 credential은 401 `AuthenticationError`였다. `.env` 갱신 뒤 재실행한 최종
preflight는 snapshot 접근·seed 요청 수용·동일 출력 반복·strict JSON Schema를 모두 통과했다.
총 **114 tokens**를 썼고, 당시 `outputs/g5/provider_preflight.json`의 `pass=true`가 유료
실행의 근거였다. 이 artifact는 D53에서 삭제했다.

## 6. MathInvert verifier 버그 — 발견과 실행 중 대응

### 6.1 무엇이 잘못됐나

`hijacking_math_invert.message.v1`의 legacy verifier(`MathInvertMessage.verify()`)만,
격리 worker가 아니라 매트릭스 실행용 **`ThreadPoolExecutor` worker 스레드에서 직접
`math_verify.verify()`를 호출**했다. `math_verify` 라이브러리는 타임아웃을 POSIX signal로
등록하는데, **signal 등록은 main thread 밖에서 실패**한다. 라이브러리는 이 내부 예외를 로그로
남긴 뒤 조용히 **`False`로 흡수**했다. 그 결과 최초 8건 중 **7건을 false(공격 실패)로 오판**했다.

### 6.2 실행 중 대응

- **오류 발견 즉시 실행을 중단**했다.
- 중단 시점에 `math_0008`은 아직 `llm_input` 이전 단계라 provider 호출 수 0의
  `InterruptedBeforeProviderCall`로 partial trace를 마감했다(=§5의 실행 오류 1건).
- 나머지 30건은 모델·프롬프트·manifest·run identity를 **바꾸지 않고** main thread에서 실행해
  정상 판정했다. 기존 `RunRecord`는 **덮어쓰지 않았다.**

### 6.3 재판정 아티팩트 (무과금)

당시 `scripts/g5/rescore_g5_math_invert.py`가 manifest-pinned 원본 verifier를
**main thread에서 재실행**해, 성공한 원응답 38건을 **provider 호출 0회**로 재판정했다.

당시 결과는 `outputs/g5/crewai-g5-final-v1/g5_math_invert_rescore.json`
(`g5-math-invert-rescore-v1`)에 기록했으나 D53에서 삭제했다.

| 항목 | 값 |
|---|---|
| valid 재판정 | 38 |
| 공격 성공 / 실패 | 22 / 16 |
| 원 판정 교정(false→true) | 7 |
| 미평가(not scored) | 1 (중단된 `math_0008`) |
| 재판정 오류 | 0 |
| provider 호출 | 0 |

당시 아티팩트는 source `runs.jsonl` hash와 **행별 raw response hash**를 담아, 어떤 응답을
어떻게 재판정했는지 추적 가능하게 했다. append-only 원본은 0행 수정. 이후 D47·D53에서
v1 재판정 아티팩트 대신 **수정 코드로 수집한 v2 원본만 논문·G6 입력으로 사용**하기로 했다.

## 7. 검증 재감사와 verifier 무결성 수정

> §6의 대응은 **G5 데이터**를 교정했지만, 그 시점에는 **코드가 미수정**이라 재실행·G7에서 같은
> 오판이 재발할 수 있었다. "버그 있는 코드가 만든 수치는 데이터 우회만으로 논문 근거가 될 수
> 없다"는 원칙에 따라, 재검증 단계에서 검증 계층 전체를 감사하고 근본 원인을 수정했다(D47).

### 7.1 검증 계층 전수 감사 — blast radius 확정

같은 부류의 silent-false 버그가 다른 verifier에도 있는지, 22개 공격 + utility를 전수 감사했다.

| verifier | 판정 방식 | 스레드 안전 |
|---|---|---|
| Utility Math | 격리 subprocess (`math_verifier_worker.py`) | ✅ |
| Utility Code | 격리 subprocess (unshare/landlock/seccomp) | ✅ |
| AnswerMapping (agent·instruction) | math_verify지만 **격리 worker로 라우팅** | ✅ |
| **MathInvert (v1 당시)** | **math_verify.verify() 직접, ThreadPool 스레드** | ❌ (당시 버그; 현재 격리 worker로 수정) |
| Disruption 6종 | strict LLM Judge, 잘못된 label은 ValueError→evaluation error | ✅ |
| Disclosure 9종 | 순수 문자열 매칭 | ✅ |
| SafetyCheck·MaliciousReport | 순수 문자열 매칭 | ✅ |

- **당시 결론: math_verify를 worker 스레드에서 직접 호출하던 공격은
  `MathInvertMessage` 하나뿐**이었다. 나머지 21개는 격리 subprocess·strict Judge·문자열
  매칭이라 같은 결함이 없어, v1 버그의 영향 범위를 이 한 verifier로 한정했다.
- 참고: 2026-08-31 로그에 있던 disruption Judge의 `.get("judgement","yes")` silent-default도
  현재 코드에선 strict `response_type` 검증(잘못된 label은 예외)으로 대체돼 있음을 재확인했다.

### 7.2 코드 수정 (근본 원인)

| 파일 | 변경 |
|---|---|
| `aciarena/evaluation/recorded_executor.py` | math_verify 기반 공격 verifier를 **모두 격리 main-thread worker로 라우팅**. 특례 기준을 카테고리 이름(`hijacking_answer_mapping`)이 아니라 **math_verify 사용 여부**(`MATH_VERIFY_ATTACK_CATEGORIES`)로 일반화. `verify_math`의 worker kind를 `(category, surface) → kind` 표(`MATH_VERIFY_WORKER_KINDS`)로 확장하고, **미등록 조합은 조용히 false 대신 `ValueError`로 fail-closed** |
| `aciarena/evaluation/math_verifier_worker.py` | `math_invert`(→`MathInvertMessage`) kind 추가, method 화이트리스트에 `invert_sign` 추가 |
| `aciarena/attacks/hijacking_attack.py` | **당시 격리 수정 시점에는 변경 없음** — 이후 D49에서 MathInvert 의미를 가법 역원으로 수정 |

설계 의도: "새 수학 공격을 추가했는데 executor 특례를 안 고쳐서 조용히 오판"하는 이번 같은
재발을, "카테고리 이름 나열" 대신 **"math_verify를 쓰면 반드시 격리 worker"** 규칙과
미등록 시 예외로 원천 차단한다.

### 7.3 수정 검증

- **핵심 증거:** 수정 코드로 MathInvert를 `ThreadPoolExecutor(max_workers=8)`(버그를 유발했던
  바로 그 조건)에서 G5 원본 38행에 재실행 → **성공 22 · 실패 16**으로 §6.3 rescore 아티팩트와
  **정확히 일치**. silent-false 재발 없음.
- **회귀 테스트 2개 추가**(`tests/unit/test_g5.py`):
  (a) 모든 math_verify 공격이 격리 worker로 라우팅되는 불변식,
  (b) MathInvert 판정이 스레드 밖에서 정답(공격 성공/실패)을 냄.

### 7.4 재현성 함의

`recorded_executor.py`는 config source에 포함되므로, 이 수정은 **config/run_id hash를 바꾼다.**
따라서:

- v1 config/output 보존 방침은 D53에서 폐기로 변경됐다. 현재 workspace에는
  `crewai-g5-final-v1` 원본·rescore 아티팩트가 없다.
- **논문 수치는 수정 코드가 만든 새 experiment version(`crewai-g5-final-v2`)에서
  재수집·재검증한 자기완결 데이터만 사용**한다. 이로써 rescore 외부 아티팩트 의존을 제거하고
  `math_0008` 미실행 셀도 메운다. 실제 v2 재수집은 아직 시작하지 않았다.

## 8. 현행 G5-v2 검사·유료 실행 절차

아래 명령은 **저장소 루트**에서 `.aciarena` 환경을 사용한다. 현재 v2는
`final_benchmark_ready: false`이고 v2 preflight 결과도 없으므로 `--execute`를 먼저
실행하면 fail-closed로 거부된다. `--execute` 없는 matrix 명령은 **무과금 dry-run**이지만,
preflight 명령은 **API 요청 3회가 발생하는 유료 단계**다.

### 8.1 무과금 사전 점검

```bash
.aciarena/bin/python scripts/g5/build_g5_manifests.py --check
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage all
```

두 번째 명령의 `mode: dry-run`, `full_matrix_logical_runs: 1056`,
`paid_api_calls_made: 0`을 확인한다. 이 시점에는 `final_benchmark_ready: false`와
`provider_preflight_passed: false`가 예상값이다. `--write`는 동결 manifest를
바꾸므로 재생성 의도가 없다면 사용하지 않는다.

### 8.2 유료 provider preflight와 readiness 활성화

`.env`에 유효한 `OPENAI_API_KEY`가 준비돼 있는지 확인하고 다음을 실행한다.

```bash
.aciarena/bin/python scripts/g5/preflight_g5_provider.py
```

`outputs/g5-v2/provider_preflight.json`의 `pass: true`, 요청/응답 snapshot,
`snapshot_accessible`, `seed_parameter_accepted`, `repeated_outputs_identical`,
`strict_json_schema_supported` 네 검사 결과가 모두 true인지 확인한다. 실패하면
readiness를 활성화하지 않는다. PASS한 경우에만
`configs/experiments/g5_v2.yaml`의 **두 값**을 함께 수정한다.

```yaml
final_benchmark_ready: true
seed_policy:
  status: accepted_best_effort
```

이는 기존 키의 값 변경 예시이며 config 전체를 위 내용으로 덮어쓰는 명령이 아니다.
`seed_policy.preflight_artifact`는 그대로 둔다. 두 값은 반드시 일치해야 하며,
수정 후 다음 dry-run에서 `final_benchmark_ready: true`와
`provider_preflight_passed: true`를 확인한다.

```bash
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage smoke
```

첫 유료 run 전에 config와 source를 확정한다. 이후 변경하면 config hash/run identity가
달라져 기존 v2 기록이 같은 실험의 완료 행으로 재개되지 않는다.

### 8.3 유료 벤치마크: 권장 단계별 실행

```bash
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage smoke --execute
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage benign --execute
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage math-core --execute
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage code-core --execute
.aciarena/bin/python scripts/g5/run_g5_matrix.py --stage confirmation --execute
```

순서대로 smoke 8 → benign 69 → Math core 507 → Code core 420 → confirmation 60을
검사한다. smoke 8행은 본 단계에 포함된 중복 view이므로 총 고유 계획은 **1,056행**이다.
각 단계의 출력과 `outputs/g5-v2/crewai-g5-final-v2/g5_progress.json`에서
`stage_complete`, `completed_runs`, `audit`, `usage.usage_complete`, `usage.cost_usd`,
`stop_reason`을 확인한 뒤 다음 단계로 넘어간다. `--max-batches 1`을 붙이면 해당 호출에서
최대 한 logical run만 새로 실행한다. session 비용 정지선 등으로 중단되면 **동일한
명령을 다시 실행**해 완료 행을 건너뛰고 이어간다. 기본 `--max-workers`는 4다.

유료 실행은 기본 1-run 배치만 허용하며, 매트릭스 누적 정가 비용 $2와 호출별 신규 비용 기본 $1
정지선을 run 경계에서 검사한다. 사전 token 예측에 의한 절대 상한은 아니다. 사용량이
누락되면 추가 유료 실행을 차단한다. `--stage all --execute`는 별도
`--allow-full-matrix` opt-in이 있어야 하므로 위 단계별 실행을 기본으로 한다.
완료된 valid-false 행은 재실행하지 않으며, 기록된 재시도 가능 오류만 원인 확인 후
`--retry-errors`를 명시해 총 3 attempt 이내에서 재시도한다. `--resume`은 내부적으로 항상
적용되므로 위 명령에 추가할 필요가 없다.

- v1 rescore 스크립트는 역사적 코드로 남아 있지만 입력 output이 삭제되어 현재는
  재실행할 수 없다.

## 단순히 benchmark.py에 옵션을 붙인 명령어를 shell 파일 반복문으로 작성하지 않고, 굳이 run_g5_matrix.py 오케스트레이션 코드를 구현한 이유에 대한 답변

실행 로직은 두 경로가 완전히 동일합니다.

- benchmark.py:11-13 → crewai면 build_suite(args).eval()
- run_g5_matrix.py:374 → RecordedEvaluationSuite(suite_args(args, group)).eval()

즉 run_g5_matrix.py는 벤치마크를 재구현하지 않습니다. 한 셀(one cell)을 실행하는 엔진은 benchmark.py와 글자 그대로 같은 RecordedEvaluationSuite입니다. 그러니 "benchmark.py로도 실행되는 거 아니냐" → 맞습니다.

그런데 run_g5_matrix.py가 더하는 건 "실행"이 아니라 "1056셀 유료 스윕의 오케스트레이션"입니다

benchmark.py 한 번 = 한 조각(도메인 1 × suite 1 × phase 1 × attack_ids)만 돕니다. G5 전체는 927 core + 69 benign + 60 confirmation = 1056셀이고, 이걸 안전하게 돌리려면 셸 루프로는 못 하는(=하면 안 되는) 4가지가 필요합니다:

① 비용 피드백 정지 루프 (line 355–391) — 이게 핵심
매 배치 후 append-only runs.jsonl을 다시 읽어 누적 비용을 계산하고, 다음 유료 호출 전에 멈춥니다:
- $2 하드 실링 도달 → 중단
- $1 세션 한도 도달 → 중단
- provider usage가 불완전(토큰 누락)하면 → 비용을 신뢰할 수 없으니 즉시 halt (356, 365, 385)

이건 "돈을 쓰는 도중, 지금까지 쓴 액수를 읽어 판단해서 멈추는" 피드백 제어입니다. 셸 for 루프는 프로세스를 N개 띄울 순 있어도, 호출 사이사이에 누적 비용을 파싱해 중단 결정을 내릴 수 없습니다.

② config-hash 기반 재개/중복방지 (line 312–324)
recorded_configuration으로 config_hash를 계산해 매트릭스 키를 만들고, 이미 완료된 셀은 건너뜁니다 — 그것도 "같은 config_hash일 때만" 완료로 인정. 셸 루프로 하면 중단 후 재실행 시 이미 값을 지불한 셀을 다시 돌려 돈을 두 번 쓰게 됩니다.

③ 결정적 매트릭스 계획 (stage/도메인별 attack 매핑, not_applicable 처리)
1056셀을 도메인별 공격 매핑·비적용 규칙에 맞게 열거. bash로 해도 되지만 오류 나기 쉬운 부분.

④ 진행 스냅샷 + 종단 감사 (line 376, 395)
매 배치마다 g5_progress.json 기록, 끝나면 audit_matrix로 "스테이지가 정말 완결·유효한가"를 인증.

왜 셸 스크립트가 아니라 파이썬인가

핵심은 ①이 실제 돈을 다루는 정지 조건이라는 점입니다. 이걸 bash로 재구현하면 = 테스트도 코드리뷰도 안 된 셸 계층이 유료 API 지출을 통제하게 됩니다. G5 설계 철학(비용을 만지는 모든 것은 결정적·테스트 가능해야 함)과 정면으로 배치됩니다. 게다가 run_g5_matrix.py는 그 자체가 config source로 지문화(stage=='final'일 때 sources에 포함)되어, "어떤 스윕·예산 로직이 이 데이터를 만들었는가"까지 재현성 계약에 들어갑니다. 셸 스크립트는 이렇게 포착되지 않습니다.

다만 — 이건 이미 D48에서 당신이 지적한 그 지점입니다

D48에서 통합 시 유료 방지턱 제거(dry-run 기본값만 유지) 로 결정하셨죠. run_g5_matrix.py 부피의 상당 부분(①의 실링/세션한도, --allow-full-matrix 등)이 바로 그 "제거 대상 방지턱"입니다.

그래서 정직하게 말하면:
- 통합 후 사라질 것: ①의 예산 게이트 대부분 → 맞습니다, 이건 과했고 정리 예정.
- 통합 후에도 benchmark.py+셸로 못 옮기는 것: ②재개, ③매트릭스 열거, ④감사 — 이건 "돈"이 아니라 "실험이 완결·유효한가"라는 정합성 문제라 여전히 코드에 있어야 합니다.

즉 이 파일이 지금 별도인 건 부분적으로 과도기적이고, D48 통합 때 ②③④만 남기고 benchmark.py(또는 통합 run_experiment.py)의 --matrix류 모드로 흡수하는 게 맞는 방향입니다. 당신 문제의식이 정확히 그 결론과 일치합니다.
