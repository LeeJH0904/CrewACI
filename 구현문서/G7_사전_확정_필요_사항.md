# G7 착수 전 사전 확정 사항

- 작성일: 2026-09-17
- 상태: **G7 사전 확정 종결 + 오프라인 구현 1~6단계 완료** (2026-09-19).
  CrewAI G5 core 재사용 여부는 별도 확정 대상이 아니라 사용자 운영 선택(기본: G7에서 CrewAI
  포함 전부 재실행; G6 동결은 D65 경로·버전 분리로 보존). 실모델 파일럿·전체 수집(7~8단계)은
  사용자 per-invocation 실행으로 남아 있다.
- 대상 단계: G7 CrewAI↔legacy cross-MAS 비교
- 전제: G6 CrewAI 독립 벤치 완료, Hierarchical/GH·RQ2는 G7 이후 별도 검토
- 비용 원칙: 1~6단계는 전부 오프라인·유료 호출 0회, 기본은 dry-run이다. 실모델 7~8단계는
  `--execute`를 명시해 사용자가 per-invocation으로 직접 수행한다(D64).
- 짝 문서: 검증·확정이 끝난 항목은 [G7_사전_확정_진행_사항.md](G7_사전_확정_진행_사항.md)로 이관한다. 이 문서는 **미확정 의사결정만** 유지한다.

## 1. 문서 목적

G7은 기존 legacy MAS를 CrewAI와 같은 조건 및 기록 계약으로 재실행하여 신청서의
“기존 MAS 대비 CrewAI 위치” 기여를 충족하는 단계다. 현재 G6 원본·수치·artifact에는
수정이 필요한 결함이 없지만, G7 구현과 유료 실행 전에 아래 다섯 사항을 확정해야 한다.

1. 비교 대상 MAS·domain·공격 target 범위
2. G7 비교 지표의 분모와 오류·unknown·비적용 처리
3. legacy 공통 per-row 실행·기록 계약
4. 파일럿 규모·통과 기준·비용 승인 절차
5. G6 동결 artifact 보존 및 G7 버전 분리

이 문서는 확정이 필요한 항목을 정리한 초안이며 기존 `DECISIONS.md`의 결정을 자동으로
변경하거나 새로운 결정을 확정하지 않는다. 최종 승인 내용은 구현 전에 새 결정 항목으로
`DECISIONS.md`에 기록하고 관련 가이드와 동기화한다.

## 3. 확정 사항 2 — G7 비교 지표의 분모와 상태 처리 (✅ 구현 검증 완료)

### 3.1 확정된 지표·분모 규칙

- **헤드라인(논문 규칙, D30/D54):** 단순 비율. 빈 응답·실행 오류·평가 오류·미호출·미주입은
  모두 **실패(0)** 로 세고 `not_applicable`은 제외하지 않는다. judge 애매 시 논문 기본값을
  따른다(논문 exact parity가 아니라 정성 참조이므로 차이는 방향과 함께 설명).
- **진단(valid-only 분해, D54):** G6와 동일하게 unknown/error/NA를 분모에서 제외한 값을
  **별도 보고**한다(두 리포트 분리). CrewAI 원본과 모든 legacy 원본에 같은 규칙을 적용한다.
- 논문은 not_applicable·unknown·error 개념 자체가 없어(모두 0/1로 붕괴) 세부 엣지 기준을
  주지 않는다. 따라서 진단 레이어의 제외 규칙은 **우리 자체 기준**임을 명시한다.

## 4. 확정 사항 3 — legacy 공통 per-row 실행·기록 계약

### 4.1 구현 전 요구 범위와 현재 반영

기존 legacy 경로는 suite 단위 평균만 반환했다. 2026-09-19 G7 adapter가 아래 요구를
공통 per-row 계약으로 구현했으며, 기존 legacy 실행·verify 의미는 재사용한다.

- manifest의 정확한 `task_id`·`attack_id` 단위 선택
- model/Judge/config/source/dependency hash 동결
- 논리 run ID, attempt, resume와 허용 오류 retry
- 실행·utility·attack 상태 분리
- raw/normalized 응답, 최종 응답 source, target·payload 증거
- Judge 입력·출력 및 사용량 per-row 기록
- task 하나의 실패가 전체 suite를 중단하지 않는 오류 격리
- 동일 output directory의 `runs.jsonl`·`messages.jsonl`·config snapshot·audit

**접근·스키마 일반화는 확정([진행 C7](G7_사전_확정_진행_사항.md), D62).** 방식은 (A):
legacy 실행·verify 재사용 + recording 계층 후크 이식(신규 실행기 미신설), 출력은 CrewAI와
동일 포맷. `RunRecord`/`MessageRecord`는 **in-place 상위집합 확장**으로 일반화한다
(`topology` enum 확장, `malicious_agent`·`response_agent`=`Nonempty`, `implementation`+`legacy`,
message `phase`+`turn`, `schema_version`='1.0' 유지). 읽기 경로가 model_validate로 재검증하므로
상위집합 확장은 G6 재감사 PASS를 보존하고, records.py는 G6 provenance 해시에도 없다. 현재 G6
집계기는 일반 mapping을 받으므로, 남은 것은 legacy row를 **생산·검증·저장하는 adapter/writer**
구현이다.

참고로 `camel`·`mad`는 `scripts/mas/`에 편의용 `.sh`가 없지만 `benchmark.py`로 정상
실행 가능함이 검증됐다([진행 사항 C2](G7_사전_확정_진행_사항.md#c2--camelmad-실행-가능성-benchmarkpy로-정상-실행-2026-09-18-확정)). 따라서 위 per-row 기록 계약은
camel/mad 특정 문제가 아니라 **모든 legacy MAS에 공통**으로 필요한 작업이다.

### 4.2 공통 row 최소 필드

> **legacy 실측 대조 완료([진행 C8](G7_사전_확정_진행_사항.md), D63).** 필드는 직결·파생·신규
> 3버킷으로 분류됐고, 실질 신규 작업은 ① task_id·attack_id 결정적 매핑 ② target_invoked/
> payload_injected 계측 ③ 오류 격리+상태 taxonomy 3종이다. legacy `verify()`가 0/1뿐이라
> 실행 오류가 아니면 `valid`로 기록하고(진단=헤드라인), 진단 해상도 비대칭은 report에 명시한다.

- 식별: experiment/run/attempt/task/MAS/implementation/phase/repetition/config hash.
- 시스템: topology, agent 수, max turn, final source, target 역할, 직접 노출 횟수.
- 공격: attack ID/category/goal/surface/payload hash, target invoked, payload injected.
- 출력: raw response, normalized response, response agent, ground truth.
- 평가: utility/attack success와 각각의 valid/unknown/error/not_applicable 상태.
- 운영: 실행 상태·오류·호출 수·Agent/Judge token·latency·timestamp.
- 메시지: 최소 task/final/evaluation과 실제 주입 증거. 기존 legacy route log의 알려진
  부정확을 전파 ground truth로 사용하지 않는다.

## 5. 확정 사항 4 — G7 실행 모델(per-invocation)과 비용 처리 (✅ 확정, 2026-09-18)

### 5.1 실행 모델 = per-invocation 수동 (C9, D64)

G7은 **per-invocation 수동 모델**로 실행한다. 진입점은 **기존 `benchmark.py`를 계승**(신규
`start.py` 미신설)해 `--mas`·`--task_domain`·`--suite`(=공격목표)·`--malicious_agents`(=target
agent)로 **MAS 1 × domain 1(math|code) × 공격목표 1(hijacking/disruption/disclosure)** 슬라이스를
하나씩 벤치하고 `runs.jsonl`로 저장한 뒤 분석한다(D59-⑤ 확장). CrewAI 전용인 통합
오케스트레이터(`run_experiment.py`)는 G7에 쓰지 않는다.

**비용 처리(D48 계승 + G7 완화):**
- D48의 유료 하드 방지턱 제거(preflight 강제·$2 상한·세션 정지선·full-matrix opt-in·batch
  정지)와 **dry-run 기본값 유지**를 그대로 계승한다.
- **G7에서는 "사전 비용 산정" 요구도 제거**한다. per-invocation 슬라이스가 작고 사용자가
  각 실행을 직접 통제하므로, 실행 전 예상 비용 제시를 게이트로 요구하지 않는다.
- 유지: `--execute` 없는 0-call dry-run 기본값, 그리고 **실측 usage(호출·토큰·정가 환산)
  per-run 사후 기록**(게이트가 아니라 provenance; G5/G6과 동일).

### 5.2 본 matrix 규모의 사전 범위(§2 확정 구성 기준)

§2 확정에 따라 구성이 고정됐다: **논문 6종 + CrewAI, MAD 제외, MetaGPT code-only·나머지
5종 both, 목표별 단일 target(malicious agent 1명)**. 따라서 agent 스윕에 의한 증가는 없다.
아래 값은 **core 1회·confirmation·파일럿·재시도 제외** 기준의 legacy 신규 logical run 추정이다.

| 구성 | legacy 신규 logical runs | 기존 CrewAI core 996행 포함 비교 행 |
|---|---:|---:|
| 논문 6종(MetaGPT code-only, 나머지 5종 both) | 5,430 | 6,426 |

산식:

- Math+Code 실행 MAS 1종: benign 69 + attack 927 = 996.
- MetaGPT Code-only: benign 30 + attack 420 = 450.
- 논문 6종: `5 × 996 + 450 = 5,430` legacy 신규 run.

기본 계획은 G7에서 **CrewAI 포함 전부를 재실행**하는 것이다(사용자 운영 선택). 이때 G7
CrewAI는 `outputs/g7/…`·`g7-…` 버전으로 나가고 G6 동결값은 독립 벤치 기록으로 그대로
보존된다(D65). CrewAI 수치가 G6(독립 벤치)와 G7(cross-MAS)에 각각 존재하는 것은 의도된
것이며 충돌이 아니다(D30: exact parity 불요). G5-v2 core 재사용은 무과금 최적화 선택지로
남지만 별도 확정 대상이 아니다. 위 수는 per-invocation 슬라이스 합산의 **총량 감각용 참고치**다.

### 5.3 사후 usage 기록 (게이트 아님, provenance)

per-invocation 실행마다 다음을 **사후에** 기록한다(사전 비용 산정·중단선은 두지 않는다).

- 실측 LLM/Judge 호출 수, input/output/total token.
- known usage 기반 정가 환산액, usage 누락 호출 수.
