# G1 구현 기록: Sequential 반환 계약과 고정 normalizer

- 완료일: 2026-09-09
- Gate 상태: **G1 완료**
- 대상 MAS: `crewai_seq_nodeleg`
- 검증 방식: 고정 응답 mock 및 오프라인 회귀(실제 모델 API 호출 0회)

이 문서는 G0 완료 직후 진행한 G1의 설계, 코드 변경, 검증 결과와 완료 경계를 독립적으로 기록한다. 전체 단계와 최신 범위는 [연구·구현 문서 색인](../../CrewAI_ACIArena_연구계획/README.md), [구현 가이드](../../CrewAI_ACIArena_연구계획/00_구현_가이드.md), [검증 및 품질 기준](../../CrewAI_ACIArena_연구계획/archive/05_검증_및_품질_기준.md)을 우선한다.

## 1. 목표와 완료 조건

G1의 목표는 기존 Sequential 파이프라인의 성공 결과를 실행기·verifier가 해석해 보완하는 암묵적 형식이 아니라, MAS 자체가 명시적이고 엄격한 공통 계약으로 반환하게 하는 것이었다. 완료 조건은 다음과 같다.

1. Solver → Reviewer → Finalizer 순서로 각 작업자를 한 번씩만 호출한다.
2. 모든 외부 Agent 호출은 `run_step()`을 통과해 `pre_step → step → post_step` 훅을 보존한다.
3. Reviewer에게는 원문·Solver 초안을, Finalizer에게는 원문·초안·검토를 전달한다.
4. 최종 원문은 Finalizer 출력에서만 취하고, 원문과 verifier 입력을 분리한다.
5. 정규화 규칙을 버전화하고 실행 설정·config hash에 포함한다.
6. mock으로 순서, context, Finalizer source, 반환 스키마를 검증한다.

이는 VQ1의 기능 충실도 중 Sequential 구조 계약을 검증한 단계이다. 선정 공격의 전체 활성화, 저장 격리, domain별 golden 및 전체 audit는 G2 범위이다. 연구 목표와 Gate의 관계는 [연구 목표 및 기여](../../CrewAI_ACIArena_연구계획/archive/01_연구_목표_및_기여.md)와 [실험 설계 가이드](../../CrewAI_ACIArena_연구계획/archive/02_실험_설계_가이드.md)를 따른다.

## 2. G1 착수 전 상태

G0에서 기준본 보존, 기반 문제 5개 해소, manifest·기록 계약, 공격 factory, JSONL writer, recorded executor, Code 격리 verifier, 개발 설정·Judge·의존성 lock을 완료했다. G0 최종 회귀는 76개였으며, 다음 개발 대상은 표준 반환 계약과 normalizer로 명시되었다. 세부 이력은 [Project_log.md](../../Project_log.md)와 [DECISIONS.md](../../DECISIONS.md)에 남아 있다.

G1 전의 Sequential은 최종 결과에 `response`를 넣었지만, 반환 정보의 스키마를 강제하지 않았다. 대화 경로는 `edges`로 남았고 `conclude()`는 내부 `args`를 그대로 반환했다. recorded executor는 MAS의 `response` 문자열이 trace의 Finalizer 출력과 같은지만 확인한 뒤 `raw_response`와 `response_agent`를 실행기 측에서 보완했다. 이때 normalizer 표기는 `identity-v1/existing-verifier-extraction`이었으며, 원문과 verifier 입력이 실질적으로 같았다.

따라서 G0의 최소 순서·context 회귀가 통과했더라도 다음은 아직 보장되지 않았다.

- MAS 반환의 필수 field 및 extra field 금지
- `raw_response` 원문 보존과 정규화된 `response`의 분리
- 반환 계약 자체의 Finalizer source 불변식
- 대화 route의 개수·순서·방향·phase 강제
- normalizer 버전·소스가 config hash에 반영되는 재현 가능한 경계

## 3. 성공 반환 strict schema

[반환 스키마](../../aciarena/mas/crewai/schemas.py)에 `SequentialSuccessResult`와 `ConversationEntry`를 추가했다. 두 자료형은 Pydantic의 `strict=True`, `extra="forbid"`, `frozen=True`를 공통으로 사용한다.

성공 반환의 top-level field는 아래 다섯 개로 고정했다.

```python
{
    "raw_response": str,
    "response": str,
    "response_agent": "finalizer",
    "conversation": list[ConversationEntry],
    "status": "success",
}
```

`SequentialSuccessResult` 검증은 자료형과 literal 값 외에도 다음 불변식을 강제한다.

- `conversation`의 경로는 정확히 네 개이며 정의된 순서와 일치해야 한다.
- 마지막 conversation entry의 `content`는 `raw_response`와 일치해야 한다.
- `response_agent`는 `finalizer`, `status`는 `success`만 허용한다.
- 정의되지 않은 field와 유연한 타입 변환을 허용하지 않는다.

이 schema는 **성공 경로**의 계약이다. Agent·provider·protocol 오류를 `status=success`인 가짜 결과로 바꾸지 않는다. 예외는 recorded executor의 기존 오류 경계에서 partial trace와 함께 `RunRecord`의 `model_error`, `timeout` 또는 `protocol_error`로 마감한다. 정답 여부와 공격 성공 여부는 실행 `status`가 아니라 별도의 utility/attack 평가 field로 기록한다. 레코드 전체 원칙은 [평가·데이터 가이드](../../CrewAI_ACIArena_연구계획/archive/04_실험_평가_기준_및_데이터_가이드.md)를 따른다.

## 4. Sequential 순서, context, conversation

[순차 MAS 구현](../../aciarena/mas/crewai/sequential_mas.py)은 `max_turn=1`을 유지한다. `bootstrap()`은 query와 대화 상태를 초기화하고 user → solver task를 남기며, 실제 작업자 호출은 하지 않는다. 하나의 `step()`이 전체 파이프라인을 한 번 실행한다.

| turn | sender → receiver | phase | `content` | 다음 Agent의 실제 context |
|---:|---|---|---|---|
| 0 | user → solver | `task` | 원문 query | Solver는 query를 `run_step()`으로 수신 |
| 1 | solver → reviewer | `context` | Solver 초안 | Reviewer는 `Original task` + `Proposed solution` + 검토 지시를 수신 |
| 2 | reviewer → finalizer | `review` | Reviewer 검토 | Finalizer는 `Original task` + `Proposed solution` + `Review` + 최종화 지시를 수신 |
| 3 | finalizer → user | `final` | Finalizer 원문 | 반환 계약의 `raw_response` source |

세 Agent는 모두 `get_agent(...).run_step(...)`으로 호출된다. 이로써 기존 ACIArena의 `pre_step`·`post_step` 공격 hook을 건너뛰지 않는다. `conversation`은 Agent에게 실제로 전달된 핵심 산출물의 route를 순서대로 보존한다. Reviewer·Finalizer의 완성된 LLM 입력은 위 산출물과 원문을 명시적인 템플릿으로 합친 것이며, recorded trace의 `llm_input`에서 별도로 관찰할 수 있다.

## 5. Finalizer source와 원문 보존

Finalizer의 `run_step()` 반환값을 변경하지 않고 다음 세 곳에 원문으로 보존한다.

1. MAS 반환의 `raw_response`
2. `conversation`의 final entry `content`
3. recorded 경로의 final `MessageRecord.content` 및 최종 `RunRecord.raw_response`

MAS schema는 final conversation 원문과 `raw_response`의 일치를 검증한다. recorded executor는 다시 `raw_response == RunTrace.final_output`인지와 `response_agent == "finalizer"`인지 확인한다. 따라서 다른 Agent의 응답이나 실행기가 임의로 만든 문자열이 성공 결과의 Finalizer 출력으로 기록될 수 없다.

## 6. `text-envelope-v1` 정규화 계약

[응답 normalizer](../../aciarena/evaluation/normalizers.py)는 `NORMALIZER_VERSION = "text-envelope-v1"`으로 고정했다. 이 계약은 답을 추출하거나 새로 쓰는 계층이 아니라, MAS→verifier 경계의 전송 형식 차이만 정리한다.

변경하는 항목은 다음 세 가지다.

- 문자열 앞의 UTF-8 BOM `\ufeff` 제거
- CRLF(`\r\n`)와 CR(`\r`)을 LF(`\n`)로 통일
- 전체 문자열의 양끝 공백 제거

보존 경계는 다음과 같다.

- 본문 내부의 공백·줄바꿈·설명 문장
- Markdown/code fence와 Code 본문
- 수식 표현이나 Math/Code 답안의 형태
- 주입된 payload, 공격 문자열 및 공격 증거

빈 문자열이나 공백·줄바꿈만 있는 문자열은 정규화 결과 `""`로 허용한다. 문자열이 아닌 값은 `NormalizationError`로 거부한다. Math 정답 수식, Code block, 설명 부분을 추출하는 책임은 이 normalizer가 아니라 버전이 고정된 기존 task verifier에 남겨 둔다. 이로써 normalizer가 정답 판정이나 공격 증거를 조용히 변경하지 않게 했다.

## 7. recorded executor 연결

[기록 실행기](../../aciarena/evaluation/recorded_executor.py)에서 MAS 반환값을 실험 경계에서 다시 검증한다.

```text
Finalizer 원문
  ├─ raw_response ─────────────────────→ final message / RunRecord.raw_response
  └─ text-envelope-v1 → response → task.set_answer / attack.set_answer → verifier
```

실행기의 검증 및 연결 순서는 다음과 같다.

1. 실험 계약의 `normalizer`가 구현 버전과 다르면 Agent를 호출하기 전에 거부한다.
2. MAS 반환값이 정확히 다섯 field를 갖는 dict인지 확인한다.
3. `raw_response`·`response`·`conversation`의 자료형과 `status=success`를 확인한다.
4. `response == normalize_response(raw_response)`인지 확인한다.
5. trace의 final 원문, `raw_response`, `response_agent=finalizer`의 일치를 확인한다.
6. 검증이 끝난 결과에 query·ground truth를 추가해 task/attack verifier에 전달한다.

계약이 틀리면 `protocol_error`로 마감하고, trace에 Finalizer 원문이 있는 경우 `RunRecord.raw_response`에 보존한다. 검증되지 않은 `response`와 `response_agent`는 기록에 정상 결과처럼 남기지 않는다.

[실험 설정](../../configs/experiments/core.yaml)에 `normalizer: text-envelope-v1`을 추가했고 [설정 검증기](../../aciarena/evaluation/configuration.py)가 이 값을 G0 개발 계약의 필수 값으로 검사한다. recorded executor의 config snapshot에는 normalizer ID와 [normalizer source](../../aciarena/evaluation/normalizers.py), [schema source](../../aciarena/mas/crewai/schemas.py)의 hash가 포함된다. 따라서 정규화 규칙이나 schema 소스가 바뀌면 `config_hash`도 바뀐다.

## 8. monotonic timestamp 보정

G1 회귀 검증 중 WSL의 system wall clock이 attempt 시작 후 뒤로 보정되면, 동일 attempt의 message `created_at`이 `started_at`보다 앞서거나 `finished_at`이 중간 message보다 앞서 writer audit이 간헐적으로 실패하는 문제를 재현했다.

해결 방식은 attempt 시작 시점의 UTC wall time을 한 번 기준으로 잡고, 그 후 message와 종료 시각은 같은 기준에 `time.monotonic()`의 경과시간을 더해 생성하는 것이다. [RunTrace](../../aciarena/mas/crewai/message_bus.py)는 시각 함수를 주입받아 모든 message에 같은 attempt clock을 사용하고, `finished_at`도 같은 함수로 생성한다.

이 보정은 **한 attempt 내에서** `started_at ≤ message.created_at ≤ finished_at`을 안정적으로 유지하려는 운영 수정이다. 모델, prompt, verifier, 지표, 실험 범위를 변경한 것이 아니며 서로 다른 attempt 간의 전역 절대 시각 순서를 별도로 보장한다고 주장하지 않는다.

## 11. G1 완료 판정과 G2로 남긴 경계

G1은 성공 반환의 strict schema, 세 작업자의 각 1회 `run_step()` 순서, 원문·초안·검토 context, 네 conversation route, Finalizer 원문 source, 정규화된 verifier 입력을 mock으로 검증했으므로 2026-09-09에 완료로 판정했다. 이 판정은 Sequential 독립 구현 전체나 실제 모델 성능 검증의 완료를 뜻하지 않는다.

G2에서는 다음을 별도의 Gate 증거로 완료해야 한다.

- manifest에서 선정한 공격의 실제 활성화와 `instruction`·`agent`·`message` 세 표면 연결 증거
- 공격 후 정상 run, 병렬 mock run, 병렬 JSONL 기록에서 Agent·MAS·Attack·로그 상태 격리와 중복 부재 확인
- Math/Code의 정답·오답·설명·fence·빈 출력·timeout·공격 혼합을 포함한 domain별 normalizer/verifier golden fixture
- 평가가 `valid false`인 완료 run도 `--resume`이 건너뛰고, 허용된 일시적 오류만 새 `attempt_no`로 보존되는지의 재개 검증
- 누락 row, message `seq` 단절, 저장 실패, 미호출·미주입, 예정 matrix·domain·attack coverage 불일치를 검출하는 audit

G0에서 이 항목들의 일부 하위 기능을 이미 unit/integration test로 확인했지만, 그 증거를 G1 완료와 혼동하거나 G2 전체 Gate가 이미 통과했다고 해석하지 않는다. G2 후에도 공식 CrewAI/재구현 20-run calibration은 G3, 실제 모델 파일럿과 Hierarchical 진행 결정은 G4에서 수행한다.

## 12. 메인 에이전트 문서 검증 — 2026-09-09

- strict 다섯 필드 schema와 네 conversation route, Finalizer source 불변식을
  `schemas.py`·`sequential_mas.py`에서 대조했다.
- `text-envelope-v1`의 실제 변경 범위, 실행기 재검증, config/source hash 연결과
  monotonic attempt clock을 코드·설정에서 확인했다.
