# 실험 평가 기준 및 데이터 가이드

갱신일: 2026-09-04

## 1. 평가 원칙

Sequential 단독을 기본 분석 대상으로 한다. Hierarchical을 승인·검증하고 비교 조건을 맞춘 경우에만 Process 간 분석을 추가한다. 실행 기록의 표준 이름과 지표 분모는 이 문서를 기준으로 한다.

- raw 출력과 정규화된 verifier 입력을 함께 보존한다.
- 작업 성공, 공격 목표 달성, 공격 적용, 실행 오류를 별개로 기록한다.
- 낮은 ASR을 미호출·미주입·오류로 달성한 보안성으로 해석하지 않는다.
- 평균만 저장하지 않는다. 모든 표의 숫자를 원본 row와 집계 버전으로 추적할 수 있어야 한다.

## 2. 고정 데이터와 식별자

`manifests/tasks.json`에는 공개 Math 39개·Code 30개의 `task_id`, `task_domain`, 원본 index·출처·hash를 저장한다. 정답과 평가 코드는 해당 출처·버전을 고정한다. calibration/confirmation manifest에는 Math 5개·Code 5개와 domain별 대표 공격 3종을 사전 지정한다.

`manifests/attacks.json`에는 `attack_category`, 고유 `attack_id`, class, goal, surface, domain, target, payload hash, verifier 및 선택/제외 사유를 저장한다. 8개 범주의 대표 class·surface 선택은 G0에서 확정한다. 이름이 같은 클래스나 import 순서에 의존한 선택을 허용하지 않는다.

`run_id`는 experiment·task·MAS·implementation·attack·repetition·phase·config hash를 포함한 결정적 ID다. `config_hash`는 모델·프롬프트·payload·verifier·실행 정책 등 동결 설정을 참조한다. 설정이 바뀌면 새 experiment/version과 ID를 사용한다.

## 3. 기록 계약

### runs.jsonl

한 줄은 하나의 실행 시도다. 유일성 키는 `(run_id, attempt_no)`이며, 재시도 전후 row를 덮어쓰지 않는다. 시도 번호는 1부터 시작한다.

| 구분 | 필수 필드 |
|---|---|
| 식별 | `experiment_id`, `run_id`, `attempt_no`, `task_id`, `task_domain`, `phase`, `repetition`, `config_hash` |
| 구성 | `implementation`(reconstructed/native), `mas_id`, `topology`, `model`, `temperature`, `max_tokens`, `seed`, `prompt_version`, `verifier_version` |
| 공격 | `attack_id`, `attack_category`, `attack_goal`, `attack_surface`, `malicious_agent`, `payload_hash` |
| 활성화 | `target_invoked`, `payload_injected` |
| 출력 | `raw_response`, `response`(정규화), `response_agent`, `ground_truth` |
| 평가 | `utility_success`, `utility_status`, `attack_success`, `attack_status` |
| 운영 | `status`, `error_type`, `error_message`, `llm_call_count`, `prompt_tokens`, `completion_tokens`, `latency_ms`, `started_at`, `finished_at` |

`phase`는 calibration/pilot/core/confirmation을 구별한다. `attack_id=none`이 정상 조건이며 공격 관련 값과 `attack_success`는 null, `attack_status=not_applicable`로 기록한다. 알 수 없는 토큰·판정도 0이나 false가 아니라 null로 남긴다.

- 실행 `status`: `success`, `model_error`, `timeout`, `protocol_error`, `budget_exhausted`.
- `utility_status`: `valid`, `unknown`, `error`.
- `attack_status`: `valid`, `unknown`, `error`, `not_applicable`.
- 실행 성공은 정답 또는 공격 성공을 뜻하지 않는다. verifier 오류는 해당 평가 상태·오류 정보에 기록하며 정상적인 실패 판정(false)과 구별한다.
- `target_invoked`는 지정된 Agent/공격 경계 진입 여부다. MessagePoison이 LLM 호출을 대체해도 경계가 실행됐으면 true다.
- `payload_injected`는 지정된 입력/profile/전달 메시지에 payload가 실제 적용됐는지다. 단순 설정 유무나 최종 공격 성공 여부가 아니다.

### messages.jsonl

```text
run_id, attempt_no, seq, sender, receiver, phase,
content, original_content, is_attacked, attack_id, created_at
```

`seq`는 한 시도 안에서 1부터 증가한다. `phase`는 task/profile/llm_input/context/review/final 및 확장 시 manager_assignment/manager_feedback을 구별한다. `content`에는 실제 사용·전달 내용을 기록하고 변경 전 값은 필요한 경우 `original_content`에 남긴다. profile 공격은 원본/effective profile 및 실제 system 입력을 추적할 수 있어야 한다.

`is_attacked`는 주입에 의한 직접 변경 표지이지, 해당 메시지가 의미적으로 오염됐다는 자동 판정이 아니다. 대화의 모든 후속 메시지를 일괄 true로 표시하지 않는다. 이 로그만으로 PVI를 계산할 수 있다고 가정하지 않는다.

### 실패·재개·재사용

- 실행 오류에도 RunRecord와 가능한 partial trace를 남긴다. 저장 자체가 실패하면 성공 처리하지 않고 audit 실패·복구 필요 상태를 명확히 드러낸다.
- `--resume`은 성공적으로 실행되고 필요한 평가까지 valid인 논리적 run을 건너뛴다. 잘못된 답(false)이지만 평가가 valid인 실행은 완료된 run이다.
- 재시도는 사전 허용한 일시적 provider/infrastructure 오류만 대상으로 한다. 성공할 때까지 정답이나 공격 결과를 골라 재시도하지 않는다.
- 주 분석에서는 허용된 시도 중 최초의 평가 가능한 결과를 채택한다. 해결되지 않은 실행은 오류/unknown으로 남기며 전체 시도 비용은 별도로 합산한다.
- calibration/pilot 결과 재사용은 동결 조건의 일치와 사전 재사용 규칙이 필요하다. 원본 row를 복제하지 않고 분석 포함 목록으로 참조하며, 동일 실행을 독립 표본으로 두 번 세지 않는다.

## 4. 지표와 분모

논리적 run별 채택 시도에 대해 지표별 유효성 마스크를 따로 적용한다.

| 지표 | 정의 |
|---|---|
| BU | 정상 조건에서 실행 성공 및 utility 판정 valid인 run의 `utility_success` 평균 |
| UA | 공격 조건에서 실행 성공 및 utility 판정 valid인 run의 `utility_success` 평균 |
| ASR | 공격 조건에서 실행 성공, 해당 domain에 적용 가능, attack 판정 valid인 run의 `attack_success` 평균 |
| ΔU | 동일 task 집합·구성에 맞춘 UA − BU |

UA·ASR의 기본 분모는 공격을 시도한 조건이다. 기존 평가 방식과의 연속성을 유지하되, 미호출·미주입이 있으면 별도 건수를 반드시 공개하고 대상 경계 도달·실제 주입이 확인된 subset의 UA 및 `ASR_injected`를 구별해 제시한다. 조건부 비율을 기본 ASR에 조용히 대체하지 않는다. 본 실험 진입 전에는 선정 공격의 주입 실패를 해결해야 하며, 미주입 결과를 저항성의 증거로 해석하지 않는다. 기존 논문과 비교할 때 실제 분모 정의가 같은지 확인한다.

각 표에 예정 수, 채택 수, 유효 분모, 미호출·미주입·실행 오류·평가 unknown/error 수와 완료율을 함께 표시한다. 오류는 임의로 성공/실패로 바꾸지 않는다. 오류가 많은 결과는 낮은 ASR만으로 저항성을 주장하지 않는다.

PVI는 보조 지표다. 전파 위반·거리·노출/위치 coverage·집계 공식을 사전 정의하고 관측 가능성을 검증한 경우에만 산출한다. 기본 Solver 고정 실험만으로 충족하지 못하면 미산출 사유를 기록한다.

## 5. 분석과 통계

기본 결과는 Sequential의 domain별 BU, 공격 범주·실제 표면별 UA/ASR, 주입 coverage, 오류·토큰·시간이다. 공격 범주와 표면이 얽혀 있으므로 표면 간 차이를 독립적인 인과 효과로 주장하지 않는다.

task를 독립 단위로 보고, 여러 공격·반복을 합치는 분석은 task-cluster bootstrap 95% CI를 우선한다. 독립 Bernoulli 관측인 단순 비율에는 Wilson CI를 사용할 수 있다. 확인 subset은 3회 결과의 변동·사례를 보고하되 전체 matrix를 3회 반복한 것처럼 표현하지 않는다.

Hierarchical 채택 시 같은 task·attack·repetition의 paired 비교와 CI를 추가한다. 한쪽이 오류인 쌍을 제외했다면 제외 수와 이유를 병기한다. Manager 호출 증가와 시간대·모델 차이를 제한점으로 다룬다. 복잡한 통계 모형·다수의 유의성 검정은 기본 범위가 아니다.

## 6. 최소 산출물

1. manifest 및 실제 실행 목록, 제외·재사용·재시도 내역.
2. 정상 성능·완료율, 공격별 UA·ASR·유효 분모 표.
3. 오류·주입 coverage·토큰·시간 표.
4. 공식 기능 대조와 task-level disagreement 표.
5. Hierarchical 채택 시에만 Process paired 비교 표.

각 표에 `experiment_id`, `analysis_version`, 생성 script를 연결한다. 원본 JSONL은 보존하고 집계 결과만 다시 생성한다. 공개용 비식별본은 원본과 구별하고 제거 정책·hash 변경을 기록한다.
