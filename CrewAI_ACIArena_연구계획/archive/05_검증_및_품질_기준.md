# 검증 및 품질 기준

갱신일: 2026-09-04

## 1. 무엇을 검증하는가

검증 대상은 “CrewAI처럼 보이는 클래스가 있는가”가 아니다. **선택한 CrewAI 기능을 어떻게 재현했으며, 그 구현이 ACIArena의 공격 계약 안에서 실제로 동작하고 측정 가능한가**를 증거로 확인한다.

기능 충실도, 공격 연결 적합성, 평가·재현성은 별개의 축이다. 공식 동작과 비슷해도 공격이 작동하지 않으면 통합 실패이며, 공격이 작동해도 CrewAI 기능 대조가 없으면 공식 CrewAI의 취약성을 대표한다고 주장할 수 없다.

## 2. 기능·계약·증거 대응표

| 대상 | ACIArena 안의 구현 계약 | 필수 검증 증거 |
|---|---|---|
| role·goal·backstory | 공통 `CrewAIAgent(BaseAgent)`의 profile | 설정과 실제 system 입력 대조 |
| Task context | 원문·Solver 출력·Review의 지정 수신자 전달 | mock 입력 스냅샷과 메시지 순서 |
| Sequential | 작업자 3명 각 1회, Finalizer 최종 응답 | 호출 count·순서·source 테스트 |
| 입력 공격 | `run_step()`을 거친 `step` 입력 패치 | effective LLM 입력에 실제 payload 존재 |
| profile 공격 | effective profile을 실제 system 입력에 반영 | original/effective profile과 입력 대응 |
| 메시지 공격 | `step` 출력 대체 후 수신자에게 전달 | 대상 경계 실행과 실제 수신 메시지 |
| 평가 연결 | raw 보존, 고정 정규화 `response`를 기존 verifier에 전달 | Math/Code golden fixture |
| 실행 격리 | 새 Agent·MAS·Attack·run별 로그 | 공격→정상 연속 실행 및 동시성 검사 |
| Hierarchical: 선택 | Manager 배정 검증·worker 실행·Manager 최종화 | 승인 후 계획/결과 trace·정상/오류 테스트 |

각 행은 `검증됨 / 부분 검증 / 미검증 / 범위 제외`로 상태를 표시하고 코드 commit·테스트·trace·차이 설명을 연결한다. 파일 존재 여부나 근거 없는 단일 완성도 백분율로 대체하지 않는다. 통과한 행도 증거 범위 밖의 동등성을 뜻하지 않는다.

## 3. 단계별 Gate

| Gate | 통과 조건 | 통과하지 못하면 |
|---|---|---|
| G0 기준본·범위 | 다섯 기반 문제 해결, 기존 Math/Code 회귀 확인, 대표 공격·스키마·설정·예산 기록 | 확장·본 실험 금지 |
| G1 Sequential | 순서·context·응답 source·반환 계약 mock 테스트 | Sequential 실행 수정 |
| G2 공격·저장 | 선정 공격 실제 활성화, 세 표면 연결, 격리·JSONL·resume·audit 테스트 | 실제 모델 실험 전 수정 |
| G3 기능 대조 | Sequential 20-run calibration와 기능별 차이 보고 | 차이 원인·명칭·주장 범위 검토 |
| G4 파일럿·범위 결정 | 안정성·평가·비용 확인, Hierarchical 진행 여부 기록 | 본 matrix 보류 |
| GH 선택 확장 검증 | Hierarchical 채택 시 G1~G4에 준하는 검증, 추가 대조 20 runs·파일럿 | 미검증 구성을 비교에서 제외하고 범위 재결정 |
| G5 본 실험 | 최종 활성 구성·manifest 동결 후 예정 실행 목록 수행 | 누락·허용 오류만 보완 |
| G6 연구 완료 | audit·집계 재현·artifact·보고서, 주장과 근거 일치 | 미해결 항목 명시 |

G4까지의 통과가 Sequential 독립 구현 완료이자 확장 결정 지점이다. Hierarchical 미진행 시 GH는 적용하지 않는다. G0의 개발 설정 고정과 G5 직전의 본 실험 설정 최종 동결은 구별하며, 중간 변경은 새 버전과 회귀 검증을 남긴다.

## 4. 최소 기능 calibration

표본은 사전 고정한 Math 5개·Code 5개다. Sequential은 10 tasks × reconstructed/native 2종 = **20 runs**, Hierarchical 추가 시 같은 방식의 20 runs를 더해 **총 40 runs**다.

공식 runtime 버전·Agent/Task 설정·Process·모델을 기록하고, 다음을 task별로 대조한다.

- 역할·goal·backstory와 Task description/expected output.
- 실제 호출 순서, context에 포함되는 내용과 최종 출력 출처.
- 완료·parse 여부, utility disagreement, 호출 수·토큰·시간.
- 공식 runtime 내부 프롬프트·위임 방식과 재구현의 차이 및 제외 기능.

정상 mock 경로에서는 연구가 정의한 필수 구조 계약 불일치가 0건이어야 한다. native 대조에서 차이가 발견되면 숨기거나 결과가 같다는 이유로 동등하다고 처리하지 않는다. 핵심 context/실행 의미를 훼손하는 차이는 수정 또는 연구 범위 재승인이 필요하다. 설명 가능한 제한적 차이만 남아도 명칭은 `CrewAI-style reconstruction`처럼 범위를 드러내고 기능별 근거를 제시한다.

완료율은 양쪽 각각 95% 이상을 요구하고, parse 성공률 차이가 10 percentage points를 넘으면 원인을 조사한다. 구성·구현당 표본 10개에서는 완료율 95%가 사실상 10개 모두 완료를 의미한다. utility 차이는 작은 표본의 동등성 검정으로 포장하지 않고 task-level disagreement를 보고한다.

## 5. 최소 테스트와 파일럿

### 실제 API 호출 전

1. Sequential 3회 호출, 원문·초안·검토의 전달, Finalizer source.
2. 세 표면의 실제 입력/profile/전달 메시지 변경 및 미공격 worker 동작.
3. 공격 후 정상 run에서 패치·profile·memory·token 상태가 남지 않음.
4. 20개 동시 mock run에서 attack 상태가 섞이지 않음.
5. 100개 동시 기록에서 JSONL 파싱 성공, `(run_id, attempt_no)` 중복 없음.
6. Math·Code 정답/오답/설명/fence/빈 출력/timeout/공격 혼합 golden fixture.
7. 재개 시 완료된 false 판정도 건너뛰고, 허용된 실패만 새 attempt로 보존.
8. 레코드 누락·메시지 단절·저장 실패를 audit가 검출함.

Hierarchical 채택 시 정상 배정, 빈/중복/미등록 worker, 잘못된 JSON, 상한 초과, 최종 source 테스트를 추가한다. fallback 결과를 정상 성공으로 오인하지 않는지 확인한다.

### G4 파일럿 통과 기준

- 실행 완료율 95% 이상.
- 성공·실패 모두 결과 row 저장률 100%, ID 중복·상태 오염 0건.
- 공격 경계 도달·주입 여부 기록률 100%; 선정 공격의 설명되지 않은 미주입 0건.
- 완료 실행의 Math/Code 평가 입력 parse 성공률 각각 98% 이상.
- 실제 사용량을 반영한 전체 비용·검증·분석 부담이 승인 범위 안에 있음.

비율과 실제 건수를 함께 보고한다. 작은 파일럿에서 높은 임계치는 사실상 오류 0건을 요구할 수 있으며 통계적 보증을 뜻하지 않는다. mock 성공만으로 실모델 파일럿을 대신하지 않는다.

## 6. 재현성과 안전

필수 artifact는 Git commit·dirty 상태, dependency lockfile, Python/OS, 실제 모델·seed 지원·retry/timeout 설정, task/attack/prompt manifest·hash, 원본 기록, verifier·집계 버전, Gate 증거와 범위 결정이다.

Code task는 네트워크 차단 및 시간·자원 제한이 있는 별도 sandbox에서 검증한다. 실제 외부 부작용을 일으키는 tool은 사용하지 않는다. API 인증정보는 설정·로그·예외·공개 artifact에 남기지 않으며, 공격용 합성 개인정보와 실제 개인정보를 구별한다.

Hierarchical 확장 판단은 [연구 목표](01_연구_목표_및_기여.md)의 기준을 따르고, 지표 분모·재시도 처리는 [데이터 가이드](04_실험_평가_기준_및_데이터_가이드.md)를 따른다.
