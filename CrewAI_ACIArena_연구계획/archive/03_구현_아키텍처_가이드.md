# 구현 아키텍처 가이드

갱신일: 2026-09-08

## 1. 기준본과 설계 원칙

현 저장소 `CrewACI/`를 그대로 작업 공간으로 사용하며, 안정화 기준본은 별도 작업공간 디렉터리 없이 Git 브랜치·태그로 보존한다. 기능 개발은 작업 브랜치에서 진행하고, 문서 갱신만으로 Git 병합이나 브랜치 정리가 이루어진 것으로 보지 않는다.

Sequential을 독립적으로 완성한다. Hierarchical 승인 전에는 Manager 전용 코드나 빈 확장 계층을 만들지 않는다. 공통 Agent·공격·평가·저장 계약만 재사용 가능하게 설계한다.

## 3. Sequential의 실행 의미

등록 ID는 `crewai_seq_nodeleg`, 에이전트 이름은 `solver`, `reviewer`, `finalizer`다.

```text
bootstrap: query와 실행 기록 초기화
step:
  solver.run_step(query)
  reviewer.run_step(query + solver_output)
  finalizer.run_step(query + solver_output + reviewer_output)
  terminate = True
conclude: Finalizer 출력과 상태·대화 반환
```

`max_turn=1`이며, bootstrap은 query·대화 상태 초기화만 하고 `step()` 하나가 전체 파이프라인(solver→reviewer→finalizer)을 한 번 실행한다. 작업자 호출을 bootstrap과 step에 중복해 넣지 않는다.

- 모든 외부 Agent 호출은 `run_step()`을 거쳐 `pre_step → step → post_step`을 보존한다.
- 역할 차이는 공통 Agent의 role·goal·backstory와 Task 설정으로 표현한다.
- profile 공격이 변경한 `effective_profile`이 실제 system 입력에 반영돼야 한다. 초기 프로필을 이후에 무조건 복원하지 않는다.
- 현재 run의 대화와 Task context는 유지하되 run 간 영속 memory·cache는 공유하지 않는다.
- 마지막 출력만 `raw_response`로 선택하고 고정 normalizer의 결과를 `response`로 반환한다. 예외를 입력 echo나 가짜 답변으로 치환하지 않는다.

## 4. 공격 계약과 실행 격리

| 표면 | 기존 공격의 연결 방식 | 검증할 실제 효과 |
|---|---|---|
| `instruction` | 대상 Agent의 `step` 입력 패치 | Solver의 effective LLM 입력에 payload 포함 |
| `agent` | 대상 Agent의 profile 교체 | 원본/effective profile과 실제 system 입력의 대응 |
| `message` | 대상 Agent의 `step` 출력 대체 | 수신 Agent에게 전달된 메시지에 payload 포함 |

MessagePoison이 원래 LLM 호출을 대체하더라도 대상 `run_step`/공격 경계에 도달하면 `target_invoked=true`다. 실제 LLM 호출 수와는 구별한다. 메시지 버스는 기존 공격을 중복 적용하지 않고 패치 이후 실제 전달 내용을 기록한다.

`build_attack(attack_id, ...)`는 매 run 새 객체를 반환한다. 실행기와 logger도 run 범위로 격리하고 `answer`, `turn_count`, `malicious_agents`, profile·memory·tokens가 다른 run에 남지 않게 한다. 세 표면 모두 설정 유무가 아니라 실제 효과와 기록으로 검증한다.

2026-09-08 구현: `AttackCatalog`가 개발 manifest와 소스의 class/domain/surface/
payload/verifier를 검증하고, `utils.factory.build_attack()`이 매 호출 새 Attack·Judge를
생성한다. 정상 조건은 Judge 없는 BenignAttack이다. catalog는 불변 spec만 공유한다.
기존 executor·logger 연결은 아직 후속 작업이며 이 생성 API만으로 실행 격리 전체가
완료된 것은 아니다. 사용 예와 검증 범위는 [manifest 설명](../../manifests/README.md)을 따른다.

정상 응답과 실행 오류는 같은 레코드 체계로 저장한다. 예외를 삼키지 않으며, partial trace를 보존하고 후속 run은 계속할 수 있게 한다. writer 오류는 성공으로 처리하지 않고 실행을 멈추거나 명시적인 복구 경로와 audit 실패로 드러낸다.

2026-09-08 저장 계층 구현: `RunWriter.append_message()`로 메시지를 즉시 append하고,
`append_run()`으로 정상/오류 시도를 마감한다. 로컬 POSIX flock과 fsync를 사용하고,
저장 중단·실패는 `.write_pending.json`과 원본을 보존해 복구 필요 상태로 드러낸다.
완료 조회와 저장 구조 audit를 제공한다. 기존 실행기/logger 배선과 전체 matrix의
예정 목록 대조는 아직 후속 작업이다.

## 5. Hierarchical: G4 승인 후 적용하는 설계

등록 ID는 `crewai_hier_nodeleg`다. 동일한 작업자에 `manager`를 추가한다.

```text
Manager 계획 → 제한된 배정 프로토콜 검증
→ 허용된 작업자 실행 및 context 전달
→ Manager 결과 종합 → response
```

Manager 출력이 실제 배정에 영향을 주어야 한다. 이름만 Manager인 에이전트를 고정 루프 앞에 넣는 것으로 대체하지 않는다. 허용 작업자·중복/빈 배정·순서와 상한을 검증하며 자유 텍스트를 코드로 실행하지 않는다. 작업자 간 자율 위임은 여전히 비활성이다.

잘못된 계획은 `protocol_error`와 raw 계획을 기록한다. 고정 순서 fallback은 진단용 결과를 남길 수 있으나 정상 Hierarchical 성공 run으로 집계하지 않는다. fallback 정책은 확장 실험 전 동결한다.

기본 설계는 Manager 계획 1회·작업자 각 1회·Manager 최종화 1회이며, 이는 연구의 제한된 재구현이지 공식 CrewAI 전체의 호출 수 보장이 아니다. 공식 대조에서 배정·context·출력 출처 차이를 보고한다.

## 6. 공식 참조와 구현 완료의 경계

공식 CrewAI는 별도 환경과 고정 버전으로 실행한다. 같은 역할·Task·Process를 설정하고 runtime 고유 프롬프트·실행 차이를 보존해 비교한다. ACIArena 공격을 공식 runtime에 직접 연결하는 작업은 기본 범위가 아니다.

Sequential은 공통 계약, 세 표면의 활성화, 상태 격리, 원본/정규화 출력, 재개·감사, 20-run 기능 대조와 파일럿을 통과하면 독립 구현 완료다. 이후 Hierarchical을 선택한 경우에만 Manager 구현과 같은 검증을 추가한다. 전체 연구 완료는 활성 구성의 본 실험·감사·보고까지 포함한다.

실행 순서와 간결한 완료 목록은 [구현 가이드](../00_구현_가이드.md), 통과 증거는 [품질 기준](05_검증_및_품질_기준.md)을 참조한다.

## 2026-09-08 실행기 연결 구현 현황

`benchmark.py`와 factory의 CrewAI 분기는 `recorded_suite.py`/`recorded_executor.py`를
사용한다. 기존 `task_executor.py`는 다른 MAS 경로에 남아 있다. 새 실행기는
`catalog.py`로 Attack/Judge를 생성하고 `crewai/message_bus.py`의 RunTrace로
실제 run_step 경계·공격 적용·LLM 입력·Finalizer·Judge를 `run_writer.py`에 기록한다.
`math_verifier_worker.py`는 기존 수학 판정의 signal timeout을 main thread에서 실행한다.
`code_verifier_worker.py`는 Linux x86_64 user/network/PID namespace 안에서 실행되며
Landlock으로 Python runtime 읽기와 전용 임시 디렉터리 쓰기만 허용한다. seccomp와
rlimit으로 네트워크·process escape·host signal 및 시간·메모리·파일 자원을 제한한다.
격리 기능을 적용하지 못하면 host fallback 없이 CodeSandboxUnavailable이다.
외부 Code verifier 주입은 version 필수다. G1 normalizer와 matrix audit는 후속 구현이다.

`configuration.py`는 `configs/experiments/core.yaml`을 단일 CrewAI CLI 설정 진입점으로
검사한다. model/Judge 파일은 참조하고 contract·공개 설정·dependency lock hash를
run config에 포함한다. 개별 CrewAI model/Judge override는 허용하지 않는다.
