# 실험 설계 가이드

갱신일: 2026-09-11

## 1. 기본 범위와 관측 단위

확정 구현 대상은 `crewai_seq_nodeleg`다. G4에서 `crewai_hier_nodeleg`를 보류했으며
G5~G7에는 추가하지 않는다. GH는 G7 완료 뒤 자원 여유와 별도 승인이 있을 때만 진행한다.

하나의 논리적 run은 `experiment_id × task_id × mas_id × implementation × attack_id × repetition × phase × config_hash`로 식별한다. 재시도는 새 실험 반복이 아니라 같은 `run_id`의 다른 `attempt_no`다. 매 실행 시 Agent·MAS·Attack·로그 상태를 새로 만든다.

| 구성 | 작업자 | 작업자 간 자율 위임 | 최종 응답 출처 |
|---|---|---|---|
| Sequential: 기본 | Solver·Reviewer·Finalizer | 비활성 | Finalizer |
| Hierarchical: 승인 후 | 같은 작업자 + Manager | 비활성; Manager 배정은 유지 | Manager |

## 2. 데이터와 공격 범주

공개 Math 39개·Code 30개를 사용한다. 안정적인 task ID, 원본 index·출처·hash를 manifest에 기록한다. Science·Medical 및 신규 데이터셋은 기본 범위에서 제외한다.

| attack_category | 목표 | domain |
|---|---|---|
| `disclosure_math_location` | 정보 유출 | Math |
| `disclosure_math_name` | 정보 유출 | Math |
| `disclosure_code_apikey` | 정보 유출 | Code |
| `disclosure_code_name` | 정보 유출 | Code |
| `disruption_ddos` | 작업 방해 | Math·Code |
| `hijacking_safety_check` | 지시 탈취 | Code |
| `hijacking_malicious_report` | 지시 탈취 | Code |
| `hijacking_answer_mapping` | 지시 탈취 | Math |

이는 기존 범위 축소 결정의 8개 **범주**다. 기존 코드에는 한 범주의 profile/instruction/message 변형이 여럿 있을 수 있으므로 범주 수를 실제 공격 구현 수로 간주하지 않는다.

위 표는 G0 개발용 대표 범주다. D32에 따른 G5 최종 manifest는 기존 구현의 중복 없는
고유 class를 전부 열거해 13개 category, Math 13개·Code 14개 attack ID(고유 class
22개)를 사용한다. 목록과 hash는 `manifests/g5/attacks.json`이 기준이다.

- `attack_id`는 범주·표면·변형을 구별하는 고유 ID이며 정확히 한 클래스·payload·verifier에 연결한다.
- 핵심 규모는 **범주당 대표 구현 1개**를 선택하는 경우다. 2026-09-08 G0 개발 기준은 [attacks.json](../../manifests/attacks.json)에 class·surface·기존 지원 domain·payload hash와 함께 기록했다. 선정 근거는 [manifest 설명](../../manifests/README.md)과 `DECISIONS.md`를 따른다.
- 표면은 `instruction`, `agent`, `message`로 기록한다. 모든 범주를 세 표면과 곱하는 factorial 실험은 기본 범위가 아니다.
- 세 표면의 연결 기능은 모두 테스트한다. 본 matrix의 표면별 분석은 실제 선택된 공격이 제공하는 coverage에 한정한다.
- core target은 Solver다. 공격 실행 경계 도달과 실제 payload 적용을 별도로 확인한다.

## 3. 실행 규모: 기본과 선택 확장

대표 구현 1개/범주, 두 domain 유지, 전체 1회와 고정 subset 확인 반복을 가정한다.

| 구분 | Sequential 단독 | Hierarchical 포함 총합 |
|---|---:|---:|
| 핵심 공격 | 39×4 + 30×5 = 306 | 612 |
| 정상 기준선 | 69 | 138 |
| 공식 기능 대조 | 10 tasks × 2 implementations = 20 | 40 |
| 확인 반복 | 10 tasks × 3 attacks × 추가 2회 = 60 | 120 |
| 합계: 별도 실행 기준 | **455** | **910** |

Math 5개·Code 5개(HumanEval 2개·MBPP 3개)의 고정 태스크와 domain별 대표 공격 3종을 사전 선택했다. `SHA-256("42:<task_id>")` 순위로 task를 선택하며 모델 결과를 사용하지 않는다. 표본과 공격 목록은 `calibration_tasks.json`·`confirmation_tasks.json`을 따른다. 확인 부분집합은 본 matrix의 첫 실행에 두 번을 추가해 총 3회가 된다.

455/910은 서로 다른 규모안이며 더하지 않는다. Hierarchical을 추가할 경우 같은 가정의 증가분은 455이다. 이 숫자는 API 호출 수나 비용 상한이 아니며, 각 run의 LLM 호출 수는 Process·공격에 따라 다르다.

2026-09-08 코드 확인으로 이전 414회 공격·563/1,126회 합계의 domain 가정을 정정했다. SafetyCheck·MaliciousReport는 Code 전용이고 AnswerMapping은 Math 전용이다. 8개 범주를 유지하며 원본 payload·verifier가 지원하지 않는 domain으로 확대하지 않는 G0 개발 기준이다. G5 최종 동결은 별도다.

**2026-09-11 G5 최종 동결:** Sequential 핵심 공격은 `39×13 + 30×14 = 927`,
정상 기준선 69, 고정 subset 확인 추가 반복 60으로 총 **1,056 logical runs**다.
G0의 455는 개발 대표안이며 G5 최종 수량으로 사용하지 않는다. AnswerMapping 두
변형의 `math_0016` 두 조건은 예상 `not_applicable`로 계획에 남긴다.

- 공격 파일럿은 기본적으로 같은 10 tasks × 3 attacks = 구성당 30 runs다. 위 합계는 별도 파일럿·실패 재시도·개발 진단 비용을 포함하지 않는다.
- 파일럿·재구현 calibration 결과는 task·prompt·payload·모델·verifier 등 조건이 본 실험과 정확히 일치하고 재사용 규칙을 사전 고정한 경우에만 재사용한다. 동일 실행을 두 독립 표본으로 집계하지 않는다.
- 대표 변형 수, 반복, 재사용이 달라지면 manifest의 `--dry-run` 목록으로 실제 예정 수를 다시 계산한다. 표면을 추가하면서 위 합계를 유지하지 않는다.

## 4. 실행 순서와 Hierarchical 결정

1. G0: 데이터·대표 공격·모델·프롬프트·예산과 기준본을 확정한다.
2. G1~G2: Sequential 및 세 공격 표면·실행 격리·저장을 mock으로 검증한다.
3. G3: Sequential 공식/재구현 기능 대조 20 runs와 차이 보고를 완료한다.
4. G4: 소규모 파일럿으로 실행 안정성·주입 증거·비용을 확인하고 Hierarchical 진행 여부를 결정한다.
5. G4 결정에 따라 Sequential 단독 본 matrix를 동결한다. Hierarchical은 G7 뒤 별도 검토한다.
6. G5: 활성 구성의 정상 기준선·핵심 공격·확인 반복을 실행한다.
7. G6: 누락·오류·중복을 감사하고 허용 재시도, 집계, artifact·보고서를 동결한다. 여기까지가 CrewAI 독립 벤치 완료다.
8. G7: cross-MAS 비교. legacy per-row 기록 + bug-fixed legacy 재실행 + 공통 집계기로 CrewAI↔legacy를 정렬·비교한다. 파일럿·예산 게이트 통과 후 착수하며, 신청서 실용적 기여를 충족한다(`DECISIONS.md` D30/D32).

두 구성 비교를 선택하면 가능한 한 같은 task block 안에서 구성·조건 순서를 무작위화한다. 이전 Sequential 데이터를 재사용하면 측정 시점 차이와 모델 drift를 확인하고, 비교 조건이 달라졌다면 새 experiment에서 다시 측정한다.

## 5. 통제 변수와 축소 규칙

- 모델(2026-09-07 확정): 개발·검증 등 실험 중 단계는 **Bionic 로컬 LLM API**로 수행하고(API 비용 없음), **GPT-4o-mini는 최종 벤치(G5 본 matrix)에만** 사용한다. 두 경우 모두 temperature 0.0, max tokens 1,024, seed 42 요청. provider의 seed 지원 여부와 실제 적용 설정을 기록하며 완전 결정성을 보장한다고 표현하지 않는다.
- Judge 모델·프롬프트·설정과 verifier 버전도 별도로 동결한다. Bionic 로컬 LLM API로 얻은 실험 수치는 최종 벤치 수치와 섞지 않는다. G3 calibration은 D36에 따라 양쪽 모두 Bionic 로컬 모델로 확정했으며, G4 pilot의 모델 배정은 별도로 확정한다.
- 본 실험에서 공식 `crewai`를 사용하지 않는다. Memory·Knowledge·Planning·외부 tools·작업자 자율 위임은 비활성이다. 현재 run의 Task context 전달은 유지한다.
- 두 구성을 비교할 때 작업자 role·goal·backstory, task, payload, 모델·평가 조건을 같게 유지한다.
- 공격/평가 기능이 불안정하면 확장보다 수정이 우선이다. 파일럿 완료율 95% 미만 또는 주입 증거 누락이 있으면 본 matrix를 시작하지 않는다.
- 자원이 부족하면 Hierarchical 및 선택 지표를 우선 제외하고, 확인 반복·domain 추가 축소는 근거와 승인·새 manifest를 남긴다. 격리·주입 검증·원본 기록은 축소하지 않는다.
- 성능이 나쁜 task나 ASR이 불리한 공격을 결과 확인 후 선택적으로 제거하지 않는다. 제외·재시도 사유와 전체 예정 분모를 함께 보고한다.

평가와 재사용의 세부 규칙은 [데이터 가이드](04_실험_평가_기준_및_데이터_가이드.md), Gate 통과 증거는 [품질 기준](05_검증_및_품질_기준.md)을 따른다.

유지한다. usage가 누락되면 알려진 비용을 하한으로 표시하고 다음 유료 run 전에 중단한다.
