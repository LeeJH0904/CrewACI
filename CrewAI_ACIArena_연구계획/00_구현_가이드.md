# CrewAI × ACIArena 구현 가이드

갱신일: 2026-09-09. 구현용 요약 문서이며, 상세 연구·평가 근거는 [문서 색인](README.md)의 최신 가이드를 따른다.

> **결정 기록 규칙:** 개발·검증 중 새로 확정이 필요한 범위·지표·구성·설정 사항이 생기면, 그 즉시 저장소 루트의 `DECISIONS.md`에 결정일·근거·영향(연구 질문/문서)과 함께 추가한다. G4 Hierarchical·모델 배정뿐 아니라 모든 결정에 적용한다.

## 1. 먼저 고정할 공통 계약

### 1.1 활성 구성과 역할

- 기본: `crewai_seq_nodeleg` — `solver`, `reviewer`, `finalizer`.
- 선택 확장: `crewai_hier_nodeleg` — G4 승인 후 같은 작업자와 `manager` 추가.
- 공격 위치는 `solver`, 작업자끼리 자율 위임은 비활성이다.
- 기본 `mas_ids`에는 Sequential만 넣는다. Hierarchical 코드·테스트는 승인 전 필수 조건이 아니다.

### 1.2 MAS 호출·반환

모든 외부 Agent 호출은 `agent.run_step()`을 통과시켜 `pre_step → step → post_step`을 보존한다. `step()` 직접 호출, 예외 시 입력 echo, 가짜 성공 응답을 허용하지 않는다.

```python
{
    "raw_response": str,      # 최종 Agent의 원본 출력
    "response": str,          # 고정 normalizer를 거친 verifier 입력
    "response_agent": str,    # Sequential=finalizer; 선택 확장=manager
    "conversation": list[dict],
    "status": str,            # 실행 상태; 정답/공격 성공 여부와 별개
}
```

실행 상태는 `success`, `model_error`, `timeout`, `protocol_error`, `budget_exhausted`다. 오류에도 partial conversation과 `error_type`, `error_message`를 보존한다. 평가 결과는 별도의 `utility_success`/`attack_success` 및 valid/unknown/error 상태로 기록한다.

### 1.3 공격·기록·재개

- `attack_category`는 연구의 8개 범주다. `attack_id`는 표면·변형을 구별하며 정확히 한 class·payload·verifier에 연결한다. 정상 조건은 `attack_id=none`이다.
- 매 실행 새 MAS·Agent·Attack과 격리된 로그를 사용한다.
- `target_invoked`는 대상 Agent/공격 경계 도달, `payload_injected`는 지정 표면의 실제 payload 적용이다. MessagePoison이 LLM 호출을 대체하는 경우와도 구별한다.
- `runs.jsonl`에는 시도당 한 줄을 저장하며 `(run_id, attempt_no)`가 유일성 키다. `messages.jsonl`에는 같은 키와 단조 증가 `seq`를 둔다.
- `run_id`는 experiment·task·MAS·implementation·attack·repetition·phase·config hash로 결정한다. 재시도 row를 덮어쓰지 않는다.
- `--resume`은 실행 및 필요한 평가가 완료된 run을 건너뛴다. 정답/공격 결과가 false라는 이유로 재실행하지 않는다.

필드명·분모·재시도·재사용의 상세 기준은 [데이터 가이드](archive/04_실험_평가_기준_및_데이터_가이드.md)다.

## 3. 목표와 범위

목표는 **Sequential을 ACIArena 공격 계약 안에서 실행·검증·기록 가능한 상태로 완성한 뒤 Hierarchical 구현 여부를 결정하는 것**이다. 여기에 더해, 신청서의 실용적 기여를 위해 **정렬을 거친 CrewAI↔기존 legacy MAS 비교(cross-MAS)를 별도 단계 G7에서 수행**한다(`DECISIONS.md` D30/D32). G6까지는 CrewAI 독립 벤치 완료, G7이 전체 연구 완료다.

```text
설정·manifest → 새 MAS·공격 → 공격 적용·실행
→ task/attack 검증 → runs/messages 저장 → audit → 집계
```

기본 범위는 Math 39개·Code 30개, 기존 8개 공격 범주, Solver 위치, BU·UA·ASR과 최소 실행·메시지 기록이다. **도메인은 math/code로 확정(sci·medicine 제외, D28), 공격 목표는 Hijacking·Disruption·Exfiltration 3종 전부 유지(D29)한다.** 모델 사용 정책(2026-09-07 확정): 개발·검증 등 **실험 중 단계는 Bionic 로컬 LLM API로 수행해 API 비용이 없고**, **GPT-4o-mini는 최종 벤치(G5 본 matrix)에만 사용**한다. 두 경우 모두 temperature 0.0, max tokens 1,024를 쓰고 seed 42를 요청하며 실제 지원 여부를 기록한다. 로컬 실험 수치를 최종 벤치 결과로 간주하지 않는다. Judge 설정·verifier도 별도 동결한다.

공식 `crewai`는 본 실험에 import하지 않는다. 별도 참조 환경에서 10 tasks의 공식/재구현 대조를 수행한다. Sequential은 20 runs, Hierarchical까지 채택하면 총 40 runs다.

전체 1회·고정 subset 확인 반복·범주당 대표 공격 1개 가정의 개발 manifest 규모는 Sequential **455 runs**, 두 구성 **910 runs**다. 기존 domain 지원(Math 4종·Code 5종)을 확인해 이전 563/1,126의 가정을 정정했다. 별도 파일럿·오류 재시도는 포함되지 않으며 class·surface 선택과 재사용에 따라 바뀐다. 신청서의 1,356 사례와 혼동하지 않는다. 이 규모는 개발용 대표 subset 기준이며, cross-MAS 비교(G5·G7)에서는 ①에 따라 CrewAI manifest를 legacy와 동일한 math/code 전 공격 세트로 확장한다(D32). 산식·가정은 [실험 설계](archive/02_실험_설계_가이드.md)를 따른다.

## 4. 작업 공간과 코드 구조

현 저장소 `CrewACI/`를 그대로 작업 공간으로 사용한다. 안정화 기준본은 별도 작업공간 디렉터리로 복사하지 않고 Git 브랜치·태그로 보존하며, 기능 개발은 작업 브랜치에서 진행한다. 아래 구조는 `CrewACI/` 안에 갖출 목표 배치이며, 이 문서는 해당 배치가 이미 완료됐다고 가정하지 않는다.

```text
CrewACI/
├─ benchmark.py, setup.py, .env.example
├─ configs/{model.yaml,judge.yaml,experiments/core.yaml,prompts/crewai.yaml}
├─ manifests/{tasks.json,attacks.json,calibration_tasks.json,confirmation_tasks.json}
├─ aciarena/
│  ├─ mas/crewai/{schemas.py,prompts.py,agent.py,message_bus.py,sequential_mas.py}
│  ├─ attacks/                     # 기존 공격 + catalog.py
│  ├─ evaluation/                  # 기존 task/datasets + 실행·평가·저장
│  └─ utils/                       # factory/logger
├─ native_reference/{crew_factory.py,adapter.py,run_calibration.py}
├─ scripts/{build_manifests.py,audit_records.py,aggregate_results.py(후속)}
├─ tests/{unit,integration,concurrency,golden}
├─ DECISIONS.md
└─ outputs/
```

기존 MAS·task·dataset을 유지하고 `mas/__init__.py`와 `mas/crewai/__init__.py`에서 활성 MAS를 등록한다. Hierarchical 승인 후에만 `hierarchical_mas.py`, `manager_protocol.py`와 Manager 프로필·자료형·테스트를 추가한다.

## 5. 핵심 구현 명세

### 5.1 Sequential

`CrewAIAgent(BaseAgent)` 하나에 설정 기반 역할을 적용한다. 공격으로 바뀐 effective profile이 실제 system 입력에 반영돼야 하며 원본과 변경본을 추적한다.

```text
bootstrap: query·대화 상태 초기화
step:
  solver.run_step(query)
  reviewer.run_step(query + solver_output)
  finalizer.run_step(query + solver_output + review)
  return args, True
conclude: Finalizer raw output → 고정 정규화 → 반환 계약
```

`max_turn=1`로 파이프라인을 한 번만 실행한다. 현재 run의 context 전달은 유지하되 run 간 memory·cache는 공유하지 않는다. 정상 mock 경로는 작업자별 1회 호출이어야 한다.

### 5.2 공격·실행·기록

| 구성 요소 | 필수 동작 |
|---|---|
| `catalog.py`·factory | 고유 attack ID, class·domain·surface 검증, 새 객체 생성 |
| `message_bus.py` | 패치 이후 실제 입력·profile·메시지와 주입 증거 기록; 공격 중복 적용 금지 |
| `task_executor.py` | 한 run의 생성→공격→실행→검증→오류/결과 기록 |
| `records.py`·`run_writer.py` | 필수 스키마, 동시성 보호, 시도 이력·완료 ID 조회 |
| `normalizers.py` | raw 보존, Math/Code verifier 입력의 고정 정규화 |
| `evaluation_suite.py` | manifest 기반 조합 생성; 목표 단위 공격 전부 자동 선택 금지 |
| `benchmark.py`·scripts | experiment 설정, attack ID·반복 지정, dry-run·resume·audit·집계 |

instruction 입력 패치, Agent profile 변경, message 출력 대체를 각각 검증한다. “설정에 공격이 있다”만으로 주입됐다고 판단하지 않는다. 메시지 공격이 LLM 호출을 생략해도 대상 경계 도달과 실제 수신 내용을 기록한다.

`build_manifests.py --dry-run`은 API 없이 예정 조합·수를 출력한다. `audit_records.py`는
benign/core-attacks/pilot/confirmation 계획과 원본 JSONL을 대조해 누락·중복·drift·
retry·주입 증거를 검사한다. 집계는 원본을 수정하지 않고 BU·UA·ASR과 유효 분모·
미주입·오류·비용을 재계산한다. PVI는 별도 정의와 관측 조건이 확보된 경우에만 보조
지표로 사용한다.

### 5.3 공식 CrewAI 대조

`native_reference/`는 별도 의존성 환경·고정 버전에서 Agent/Task/Crew를 만들고 raw 출력·context·호출·최종 source·utility를 비교한다. 본 실험 전체를 공식 runtime으로 돌리거나 그 runtime에 ACIArena 공격을 직접 삽입하는 작업은 포함하지 않는다.

### 5.4 Hierarchical: 승인 후에만

Manager 계획→배정 검증→작업자 실행→Manager 최종화로 구현한다. Manager 출력이 실제 배정에 쓰여야 하며 작업자 간 자율 위임은 비활성이다. 계획 파싱·허용 worker·중복/빈 배정·상한을 검사한다.

잘못된 계획과 fallback은 `protocol_error`로 남기고 정상 Hierarchical 결과로 집계하지 않는다. 공식 대조에서 연구용 JSON 배정 방식과 공식 동작의 차이를 명시한다. 상세 설계는 [아키텍처 가이드](archive/03_구현_아키텍처_가이드.md)를 따른다.

G7(CrewAI↔legacy cross-MAS 비교)은 `DECISIONS.md` D30/D32에 따라 진행하며, G6까지의 CrewAI 독립 완료와 구분한다. legacy 재실행 비용이 크므로 파일럿·예산 게이트를 둔다. 비교는 논문 수치 exact parity가 아니라 동일 조건 자체 재실행과 공통 집계기의 내부 일관성에 근거한다.

## 7. 검증과 완료 정의

### Sequential 독립 구현 완료: G4

- [ ] 순서·context·source 및 공통 반환 계약이 맞는다.
- [ ] 선정 공격의 실제 적용과 세 표면 연결 증거가 남는다.
- [ ] Agent·Attack·로그가 격리되고 성공·실패 row와 partial trace를 보존한다.
- [ ] Math/Code golden, 동시성, resume·audit·재계산 테스트를 통과한다.
- [ ] 공식 기능 대조 20 runs와 차이 보고, 파일럿·비용 검토를 마친다.
- [ ] Hierarchical 범위 결정을 기록한다.

파일럿 기준은 완료율 95% 이상, 성공·실패 기록률 100%, 공격 도달/주입 기록률 100%, 설명되지 않은 미주입 0건, domain별 parse 성공률 98% 이상, 중복·상태 오염 0건이다. 비율과 건수를 함께 기록한다.

### CrewAI 독립 벤치 완료: G6

- [ ] 최종 활성 구성의 예정 목록·실행 기록이 audit와 일치한다.
- [ ] 오류·미호출·미주입·unknown을 숨기지 않고 지표 분모와 함께 보고한다.
- [ ] 허용 재시도·재사용 이력을 보존하고 동일 실행을 중복 표본으로 세지 않는다.
- [ ] 원본 JSONL에서 BU·UA·ASR·비용을 다시 계산한다.
- [ ] 코드·설정·manifest·verifier·분석 버전과 보고서 주장이 일치한다.

Hierarchical 미채택 시 두 MAS 존재를 완료 조건으로 요구하지 않는다. 채택 시에는 Manager 계약과 추가 검증·paired 비교까지 충족해야 한다. 상세 판정은 [검증 및 품질 기준](archive/05_검증_및_품질_기준.md)을 따른다.

### Cross-MAS 비교 완료: G7

신청서의 실용적 기여(기존 6종 대비 CrewAI 위치 제시)는 G7에서 충족한다. G6까지는 CrewAI 독립 벤치의 완료이며, legacy와의 비교는 별도 정렬을 거친 G7에서 판정한다. 도메인은 math/code, 공격 목표는 3종 전부이며 기준은 `DECISIONS.md` D28~D32를 따른다.

- [ ] 모든 MAS(bug-fixed legacy 7종 + CrewAI)가 동일 모델·태스크·공격 세트·judge config로 실행된다.
- [ ] legacy가 CrewAI와 같은 형식의 per-row 기록을 남긴다.
- [ ] 공통 집계기가 양쪽 원본 row에서 같은 규칙으로 BU·UA·ASR·ASR_Surface를 재계산한다.
- [ ] 토폴로지·최종 source 등 연구 변수는 제거하지 않고 통제·명시한다.
- [ ] 논문 수치는 정성 참조로만 쓰고 exact parity를 강요하지 않으며, bug-fix 등 차이는 방향과 함께 설명한다.
- [ ] legacy 대규모 재실행 전 파일럿·예산 게이트를 통과한다.

방어·신규 데이터·영속 Memory·Planning·외부 tools·작업자 자율 위임·전 위치 factorial·full native equivalence는 기본 범위 밖이다. 자원이 부족해도 공격 검증·격리·원본 기록을 생략하지 않는다.
